# GigaChat: требования и сравнение с реализацией Tutor-AI

Дата: 27.10.2026. Базовый продукт: текущие исходники Tutor-AI; при заключительной сверке README уже указывает 0.4.1. Адаптер GigaChat не изменён относительно прочитанной реализации 0.4.0: SHA256 `tutor_ai/providers.py` — `DFF8361D9303C6AE262812AD688E6896B80E42CFCBF2786D5F0BCED66525B77A`. Отчёт относится к исходникам; совпадение адаптера внутри exe отдельно не проверялось.
Статус: аналитический отчёт и требования, уточнённые по ответам заказчика. В объём включены надёжный текстовый чат, список моделей, документы/изображения и доступ PERS. **27.10.2026 заказчик сообщил о подтверждении работоспособности интеграции при тестировании**; границы подтверждения приведены в разделе 7.2. Потоковый вывод и учёт предыдущих реплик остаются открытым вопросом. В рамках подготовки отчёта код провайдера не изменялся и живые запросы не выполнялись; результат тестирования заказчика зафиксирован отдельно.

### Зафиксированный объём после ответов заказчика

- Основной режим — `GIGACHAT_API_PERS`; не менять существующие подключения других типов автоматически. Новые подключения этого сценария создаются с PERS, смена scope — осознанное изменение родителем.
- В обязательный пакет входят GC-01–15 и работа с входными документами/изображениями GC-F01–12 ниже. Отсутствие files/attachments в текущем адаптере теперь является разрывом с согласованной потребностью продукта.
- Документы/изображения трактуются как входные учебные материалы для анализа, включая ДЗ. Генерация изображений, аудио, функции, embeddings, batches, AI check и отдельный экран баланса не входят в подтверждённый объём.
- Название модели не задано. Не закреплять выдуманную модель: родитель выбирает доступную по своему PERS-подключению; поддержку документов/изображений проверять для выбранной модели. PERS сам по себе не доказывает доступность любой модели или возможности.
- Streaming GC-X02 и многотуровый контекст GC-DIALOG остаются условными задачами до ответа. Их решение не препятствует постановке остальных работ.

## 2. Качество исходного контракта

Файл содержит **16 операций**. Он похож на экспорт коллекции примеров: описания полезны, но его недостаточно для строгой контрактной проверки и генерации полноценного клиента.

| ID | Наблюдение в YAML | Последствие и требуемое решение |
|---|---|---|
| SPEC-01 | Два глобальных `servers`: API и OAuth, без разделения по операциям; OAuth представлен `POST /` | Нельзя механически выбирать любой сервер для любого пути. Явно зафиксировать OAuth URL и API base URL в нормализованном контракте |
| SPEC-02 | OAuth указывает `BearerAuth`, хотя вводное описание требует Basic; `RqUID` отмечен `required: false` | Не менять правильную реализацию Basic на Bearer. Официальная авторизация требует Basic и UUID4 RqUID; исправить аналитический/рабочий контракт, сохранить оригинал |
| SPEC-03 | Только `/embeddings` содержит `requestBody`; у OAuth, чата, загрузки файла и других POST тело формально не описано | Отсутствие поля в файле не означает, что запрос должен идти без тела. Уточнить схемы из официальных источников перед реализацией соответствующего метода |
| SPEC-04 | У 13 операций пустой `responses: {}` | Нет полноценного описания успешных/ошибочных ответов. Не заявлять строгую валидацию по этому файлу и полную OpenAPI-совместимость без нормализации и проверки валидатором |
| SPEC-05 | Схема ответа чата неполна: примеры содержат `function_call` и `functions_state_id`, отсутствующие в схеме message; `model` отмечен `format: uri` | Схему нельзя использовать как достоверный исчерпывающий тип ответа; идентификатор модели не считать URL |
| SPEC-06 | В таблице загрузки `.doc` сопоставлен MIME DOCX, а `.docx` — MIME DOC | Не переносить это соответствие в валидатор файлов; проверить актуальные форматы перед добавлением облачной загрузки |
| SPEC-07 | Пример `expires_at` во вводном тексте — 13-значное число; единица формально не описана | До реализации кеша подтвердить единицу по схеме/примеру реального ответа. В официальном вводном примере авторизации также есть 10-значное значение; не смешивать секунды и миллисекунды без явного правила |

Официальная [авторизация](https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/gigachat-api) подтверждает адреса, Basic, обязательные RqUID/scope и последующий Bearer. [Описание ошибок](https://developers.sber.ru/docs/ru/gigachat/api/errors-description) также требует UUID4 для RqUID. Это разрешение противоречий YAML, а не обнаруженная ошибка Basic-авторизации продукта.

Недоступные tools/attachments/streaming не запрашиваются. Модель выбирается из проверенного списка без обещания неподтверждённых возможностей |
| GC-14 / P2 | Нормализовать usage и безопасную диагностику | Сохранить prompt_tokens/completion_tokens/total_tokens/precached_prompt_tokens при наличии; неизвестное не заменять нулём. Сохранять ID запроса/операции и длительности без секретов и текста; необязательные X-Request-ID использовать для корреляции, X-Client-ID не заполнять персональными данными |
| GC-15 / P1 | Проверить контракт и реальное подключение отдельно | Проходят пробы раздела 7; отдельно отмечен реальный текстовый тест AT-11 с выбранным scope/моделью. Mock не выдаётся за живую приёмку |

### Продуктовое решение о диалоге

GC-DIALOG / P2: определить, должен ли репетитор учитывать предыдущие реплики. Предложение для многотурового режима: передавать ограниченный релевантный контекст текущего занятия, сохраняя роль system и разграничение доступа. Не отправлять всю семейную историю. Учитывать лимит контекста модели; при сокращении не удалять локальную историю и явно отделять сокращённый сетевой контекст от полного журнала. Это улучшение продукта, а не доказанное нарушение OpenAPI.

Последующее уточнение заказчика в [требованиях учебного процесса](learning-feedback-requirements-2026-10-27.md): **для ДЗ контекст и продолжение диалога одной работы подтверждены** (HW-06), как и путь «фото → OCR → редактирование → подтверждение → проверка». Это уточняет GC-F11: сначала распознать, затем дать исправить текст, только после подтверждения передавать на проверку. Согласия на облачное изображение и локальный оригинал сохраняются. Не приравнивать это решение к подтверждению streaming или общего контекста всех занятий.

Там же согласована предметная диагностика 27+3 с заданиями, комбинирующими несколько тем (DGN-10–13): приоритет проблем последних тестирований/ДЗ и подтверждённо пройденных тем без оценки; непокрытые темы не получают нового подтверждения. Это требования учебного движка, а не дополнительные методы GigaChat API. Генерация задания моделью сама по себе не подтверждает знания; результаты тематических компонентов проверяются раздельно. Рабочая история и прежние оценки сохраняются.

### 6.1. Обязательные требования к документам и изображениям

Дополнительная сверка: [загрузка файла](https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/post-file) подтверждает связь возвращаемого `id` с `messages[].attachments`, поддерживаемые форматы и пределы сервиса: 40 Мб для документа и 15 Мб для изображения. Это внешние пределы, а не новые лимиты продукта. Правильные MIME для DOC/DOCX в официальном описании устраняют SPEC-06. [Руководство по файлам](https://developers.sber.ru/docs/ru/gigachat/guides/working-with-files) используется для уточнения жизненного цикла; конкретные сроки хранения и статус обработки фиксируются по дополненному контракту, не выдумываются из YAML.

Текущее состояние: `documents.py` хранит оригиналы зашифрованными, ограничивает файл 8 МиБ и извлечённый текст 30 000 символов. PDF — до 30 страниц без пароля; изображения — до 25 мегапикселей. Изображения требуют ручного ввода текста, а `check_homework()` отправляет только подтверждённый текст. `send_multimodal()` возвращает unsupported. Для нового сценария нужны изменения адаптера, сервиса, согласий и UI, одного метода upload недостаточно.

### 6.2. Последовательность реализации подтверждённого пакета

1. Нормализованный контракт, PERS-настройки, жизненный цикл токена, ошибки и список моделей — GC-01–07, GC-10–11.
2. Надёжная генерация, метаданные, usage и регрессия — GC-08–09, GC-12–15.
3. Новые согласия, предпросмотр и маршруты отправки текст/оригинал — GC-F02–05.
4. Файловый адаптер, attachments, ACL, очистка и повтор — GC-F01, GC-F06–10.
5. Учебные сценарии, переход с актуальной версии и приёмка на PERS — GC-F11–12 и разделы 7–8.

Streaming и контекст текущего занятия добавляются отдельными задачами после уточнения, не включаются молча. Отдельный браузер всех файлов облачного аккаунта и скачивание чужих/произвольных облачных файлов для этого объёма не нужны.

## 7. Проверки и критерии выпуска

1. **Контракт:** нормализованный контракт валидируется; OAuth строго на auth URL, Basic только там; Bearer на API; UUID4 RqUID, form scope, Content-Type и Accept проверяются тестовым транспортом. Не посылать секрет на адрес из ответа модели или перенаправления.
2. **Токен:** первый вызов, повтор до expiry, обновление по expiry, повреждённый expiry, API 401 с успешным обновлением и повторный 401, OAuth 400 scope/401, смена секрета/scope/vault, logout/restore, одновременные обращения. Для кеша использовать управляемые часы, без ожидания 30 минут.
3. **Модели:** получение без выбранной модели, валидный пустой список, неправильные типы, недоступная модель и корректное сохранение выбора; отсутствие согласия не обходит действующую политику configured().
4. **Генерация:** обычный русский ответ, все usage-поля, пустые choices/content, функциональный пример из YAML с пустым content, завершение по лимиту, неизвестный finish_reason, ответ выше локального лимита, некорректный JSON. Результат не должен тихо терять текст или метаданные.
5. **Ошибки:** 400, 401, 402, 403, 404, 413, 422, 429, 5xx, сбой TLS, timeout, обрыв чтения, отмена до OAuth/в OAuth/в ожидании API; секрет не появляется в сообщениях, логах и диагностике. Нет безусловного повтора платной генерации после обрыва.
6. **Продукт:** родитель настраивает, ученик не читает секрет; разрешения на текст и документы; смена пользователя/restore во время запроса; нет дубликатов истории и начисления лишнего времени. Проверка GigaChat не ухудшает остальные три адаптера и отзывчивость интерфейса.
7. **Живой AT-11:** отдельная изолированная установка, выбранный заказчиком тип доступа, доверенный CA, доступная модель; получить models и один короткий текстовый ответ, записать фактические модель/usage/статусы без секретов. Действующие ключи вводятся локально. Без такого прогона выпуск обозначать как проверенный на mock, но не принятый на реальном GigaChat.

Документ не утверждает, что перечисленные проверки уже пройдены. Автоматические тесты и OpenAPI-валидатор в рамках аналитической задачи не запускались; сравнены исходники и существующие тестовые сценарии.

### 7.1. Дополнительная приёмка PERS и файлов

- Основной сценарий: родитель указывает PERS-ключ, получает список без заранее выбранной модели, выбирает доступную модель; текстовый запрос работает независимо от разрешения на оригиналы.
- Синтетические TXT/PDF/DOCX и JPEG/PNG проходят предпросмотр, отдельное разрешение, upload, проверку готовности, chat с attachments, сохранение одного результата и удаление временной копии. Для PDF со сканом/рисунком проверяется, что картинка не исчезает из запроса из-за одного лишь текстового извлечения.
- Отдельно: отсутствие каждого согласия, файл другого ученика, повреждённый/замаскированный формат, превышение каждого локального ограничения, неподдерживаемый WEBP без согласованного преобразования, старая политика длинного текста, недоступность вложений выбранной модели.
- Отказ и отмена на каждом этапе, обрыв после фактического upload, недоступный/истёкший ID, смена ключа/профиля, restore с совпадающими ID, отказ очистки и безопасный повтор. Не обещать удаление файла при ошибке запроса delete.
- Локальная история и зашифрованный оригинал открываются после удаления облачной копии, перезапуска и переноса на актуальную версию; резервная копия не требует действующего remote file_id.
- Живые проверки PERS выполняются отдельно на нейтральных тестовых материалах. Их протокол фиксирует модель, тип материала, фактические возможности и usage. До получения такого результата доступность файлов конкретной модели не объявляется подтверждённой.

### 7.2. Подтверждение работоспособности от заказчика

Дата сообщения: 27.10.2026. Источник: сообщение заказчика в текущей переписке: «При тестировании получено подтверждение работоспособности интеграции с GigaChat».

Результат учтён: **работоспособность интеграции подтверждена заказчиком по результатам его тестирования**. Это дополняет первоначальный статический анализ и не является выполненным аналитиком повторным испытанием.

| Что известно | Статус |
|---|---|
| Общий результат тестирования интеграции | Положительный, со слов заказчика |
| Согласованный целевой тип доступа | PERS; фактический scope проверенного подключения отдельно не указан |
| Проверенная версия/сборка, модель, дата самого прогона | В сообщении не указаны; дата сообщения не подменяет дату испытания |
| Текстовый запрос, список моделей, документы и изображения по отдельности | Состав выполненных сценариев не указан; отдельная приёмка каждого не утверждается |
| Обновление токена, ошибки, отмена, очистка файлов, права доступа и миграция | Покрытие проверками не описано |

Подтверждение снимает неопределённость общего пользовательского результата подключения. Оно не означает автоматического закрытия GC-01–15/GC-F01–12 или полной приёмки AT-11: для трассировки конкретных требований нужны соответствующие сценарии и результаты. Описанные в разделе 4 свойства относятся к прочитанному снимку исходников; новое сообщение само по себе не подтверждает их изменение. Повторная проверка только ради фиксации этого сообщения не требуется. При оформлении итогового протокола добавить версию, модель и перечень действительно проверенных действий, не включая секреты.

## 8. Совместимость данных при доработках

Источник обновления — последняя актуальная установленная версия, как уточнено заказчиком в требованиях к предыдущему пакету. При финальной сверке README указывает 0.4.1; перед реализацией зафиксировать источник обновления и его сборку, а не ограничиваться прежним номером 0.4.0. Сохранить семейное подключение, scope, зашифрованный Basic-ключ, разрешения, ревизию, выбранную модель и учебную историю. Access token — временный кеш нативного сеанса, не переносимый открытый секрет.

Новые поля результата делать необязательными для старых записей; старый usage не пересчитывать и отсутствующие finish_reason/фактическую модель не выдумывать. Новые сетевые параметры — с явными безопасными значениями по умолчанию; не сбрасывать согласия и не включать новые виды облачной обработки автоматически. Изменение настроек остаётся родительским с проверкой revision.

Для документов/изображений добавить отдельные выключенные согласия на передачу оригиналов; существующее согласие на подтверждённый текст сохранить в прежнем смысле. Старые работы получают отсутствие облачной ссылки, а не вымышленный file_id. После restore/переноса ссылки считаются требующими проверки; локальные оригиналы остаются основой восстановления. Очистка из одного подключения не удаляет файлы другого.

Для изменений только адаптера и дополнительных полей JSON новый номер SQL-схемы не обязателен; необходимость миграции определить по окончательной реализации. Перед обновлением сохранить полную старую установку; проверить вход, старую историю, новую запись и повторное открытие. Оптимизация кеша не должна менять формат vault или криптографические идентификаторы.
