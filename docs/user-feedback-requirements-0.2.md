# Требования по результатам пользовательского тестирования 0.1

Дата анализа: 25.10.2026. Основания: семь замечаний пользователей, ТЗ MVP 1.0, `docs/user-guide.md`, текущие `aitutor/service.py`, `aitutor/education.py`, `aitutor/storage.py`, `ui/app.js`.

Статус: **основание реализации пакета 0.2; уточнения Q-01/Q-02 закрыты ответами заказчика**. После получения ответов заказчик запросил реализацию доработок по этому документу. Первоначальный анализ выполнен по документам и исходному коду, без исследования пользовательской базы. Фактические изменения, ограничения источника адресов и результаты проверок описаны отдельно в [релизе 0.2](release-0.2.md); формулировки ниже остаются требованиями, а не протоколом испытаний.

## 1. Итоговая классификация замечаний

| № | Наблюдение | Подтверждённая причина в реализации | Классификация / связь с ТЗ |
|---|---|---|---|
| 1 | Регион и город не подставляются | В `registerFields()` обычные текстовые поля; источник классификатора и поиск не подключены | Нереализованные AUTH-002, EDU-001; закрытие обязательного требования |

| 4 | С 7-го класса нужны алгебра и геометрия | Единственный ID `math` в домене и отдельный словарь `math` в UI; каталог и история используют этот ID | Корректировка предметной модели и исходного перечня предметов MVP |

Повтор автора у двух `register` сам по себе не доказывает ошибку регистрации. Родитель может создать несколько профилей, оставаясь автором всех действий. Нельзя подменять автора именем созданного пользователя ради визуального различия записей.

## 2. Решения заказчика

### Q-01. Имена до авторизации

**Решение заказчика: разрешено хранить имя и роль в открытом локальном списке. Вопрос закрыт.** До ввода пароля показываются отображаемое имя и роль профиля; отдельный публичный псевдоним и предварительная разблокировка для этого не требуются.

Почему это необходимо решить: при текущем шифровании имя находится внутри закрытой БД. Чтобы показать его до ввода какого-либо секрета, приложению нужен отдельный доступный до входа источник подписи профиля. Это меняет объём открытых метаданных, оговорённый в архитектуре. Скрыто сохранять пароль или мастер-ключ для этой задачи недопустимо.

Разрешённый открытый набор: account ID, отображаемое имя и роль. Это явное исключение из прежнего решения скрывать все имена до входа. Пароли, мастер-ключи, школа, адрес, связи и история в открытый список не включаются. Проверка роли и полномочий остаётся внутри авторизованного нативного слоя. Конкретный формат списка и миграции — задача разработки, не дополнительный вопрос заказчику.

### Q-02. Охват и доступность классификатора

**Решение заказчика: допустим поиск через интернет. Вопрос закрыт.** Для предусмотренного российскими адресными данными поиска допускается сетевой источник; обязательная полная локальная копия классификатора и гарантированная доступность всех подсказок без сети не требуются. Фактический охват выбранного источника должен быть проверен и описан, а не обещан по умолчанию.

Конкретный источник, его охват, формат запросов, условия использования и обновления выбираются разработчиком после проверки источника. Разрешение интернет-поиска не является согласием на платную подписку. Если выбранный источник требует учётных данных, они настраиваются родителем и хранятся защищённо, а не в JavaScript. Пользователю не требуется выбирать поставщика API.

Сетевые запросы выполняются через нативный адаптер по HTTPS с проверкой сертификата. Передаются только введённый адресный запрос и ID необходимых вышестоящих адресных записей, например региона при поиске города. Имя, пароль, ID пользователя, профиль ребёнка и вся форма не отправляются. Без сети сохраняются выбранные значения и доступен явно помеченный ручной ввод. Поздний ответ поиска для прежнего региона не может заменить результаты нового выбора.

### Принятые для проекта предположения

- В ближайшей версии остаётся 7-й класс; добавление регистрации 1–6 и 8–11 классов не включается автоматически.
- Для 7-го класса используются **алгебра, геометрия, физика, информатика**. «Математика» остаётся предметом для будущих 1–6 классов и обозначением старых записей.
- Предмет ДЗ всегда явно выбран или подтверждён учеником до проверки. Автоопределение может предложить вариант, но не отменяет подтверждение и не подменяет выбор.
- Исправления журнала отображают и автора, и целевой профиль; полный UUID остаётся техническим ключом.
- Старые данные не удаляются и не переименовываются массово без предметного соответствия.

Эти предположения остаются предложениями аналитика; ответы заказчика на Q-01/Q-02 их автоматически не утверждают. Открытых уточняющих вопросов по разрешению публичного списка и использованию интернет-поиска больше нет. Выбор источника и формата хранения выполняется на техническом этапе.

## 3. Регионы и города — FB-01

### Требования

**FB-01.1.** Заменить свободный ввод региона и города на поиск с подсказками по выбранному справочнику. Пользователь выбирает конкретную запись, а не только вводит похожий текст.

**FB-01.2.** Город ищется в пределах выбранного региона. До выбора региона поиск города недоступен либо явно предлагает сначала выбрать регион. Для одноимённых записей показывается достаточно адресного контекста, чтобы их различить; выбор по первому совпадению без пользователя запрещён.

**FB-01.3.** Сохранять стабильные идентификаторы записей, отображаемые названия, источник и версию/дату справочника. Имя города не используется как уникальный ключ.

**FB-01.4.** При смене региона ранее выбранные город и связанная справочная школа теряют валидность. Интерфейс очищает зависимые выборы с понятным уведомлением; нативный слой отклоняет несогласованные идентификаторы, даже если UI передал их напрямую. При смене города повторно проверяется школа.

**FB-01.5.** Реализовать состояния «начните ввод», «поиск», «найдены варианты», «ничего не найдено», «справочник/сеть недоступны». Поиск обрабатывает регистр, пробелы и русские названия. Невыбранное значение нельзя молча считать подтверждённой записью классификатора.

**FB-01.6.** При сбое поиска введённые имя и адресные черновики не теряются. Предлагать повтор и явно обозначенный ручной ввод с признаком `manual_unverified`; ручной ввод не считается успешной работой классификатора. Интернет-поиск разрешён; без сети нельзя молча подставлять случайный город, очищать профиль или блокировать доступ к уже сохранённым данным. Полный офлайн-классификатор не является обязательством этого пакета.

**FB-01.7.** Применить поведение во всех доступных формах создания ученика, включая первый запуск и создание ребёнка родителем. Последующее редактирование профиля должно использовать те же правила при реализации AUTH-003.

**FB-01.8.** Старые строковые значения сохраняются. Автосопоставление допускается только при однозначном соответствии; иначе требуется подтверждение. Неизвестный ID из старой версии справочника не обнуляет сохранённое название и историю.

**FB-01.9.** Школы остаются отдельным справочником, связанным с адресами, согласно исходному AUTH-002. Наличие региона и города в адресном классификаторе не считается наличием в нём школ. Полное закрытие AUTH-002 требует также реализации школьного выбора; это зависимость исходного ТЗ, а не новое пожелание пользователя.

### Приёмка

- Выбор региона выдаёт список подходящих городов, выбор сохраняет ID и название и корректно отображается после повторного входа.
- Два одноимённых города в разных регионах различаются; город из чужого региона не сохраняется через прямую нативную команду.
- Смена региона инвалидирует прежний город/школу; сохранённые учебные записи не изменяются.
- При недоступности источника форма остаётся заполненной, показан честный статус и доступен повтор/помеченный ручной ввод.
- Старый профиль со строковыми адресами открывается без потери данных; неоднозначное сопоставление запрашивает пользователя.
- При отключении интернета поиск показывает недоступность источника, сохраняет форму и предлагает ручной ввод; уже выбранные адресные значения читаются локально. Тестовые записи не выдаются за официальный производственный классификатор.
- При быстрой смене региона поздний сетевой ответ предыдущего запроса игнорируется. Проверка сетевого запроса подтверждает отсутствие имени пользователя, пароля и полной регистрационной формы.

## 4. Читаемый журнал безопасности — FB-02

### Требования

**FB-02.1.** Каждая отображаемая запись содержит дату/время, понятное русское название действия, автора с именем и ролью, а для действий над другим профилем — отдельную цель с именем и ролью.

Пример: «25.10.2026, 20:56:42 · Создан профиль ученика · Автор: Анна, родитель · Профиль: Алексей, ученик». Это пример синтетических имён, а не предположение об именах в предоставленном журнале.

**FB-02.2.** UUID автора и цели сохраняются неизменными; имя является представлением. Полный ID доступен в подробностях. В основном списке короткий суффикс нужен только для различения одинаковых имён. Технический `register` переводится как «Создан профиль» с уточнением роли цели, когда она известна.

**FB-02.3.** Уточнить семантику существующей записи: `actor` — фактически действовавшая учётка, `target` — созданный/изменённый профиль. Если родитель создал ребёнка, автором остаётся родитель. При саморегистрации автор и цель могут совпадать.

**FB-02.4.** Старые события дополняются отображаемыми именами по ID в пределах разрешённого доступа. Исторические имена, которых не было в событии, не выдумываются. Для новых событий рекомендуется сохранять зашифрованный снимок имени/роли на момент действия; текущее имя можно показывать дополнительно, если оно изменилось. Приёмка удаления должна учитывать выбранную политику сохранения персональных данных аудита.

**FB-02.5.** Для отсутствующего/удалённого пользователя выводится нейтральная подпись «Удалённый профиль»/«Профиль недоступен», а не ошибка экрана и не случайное совпадение по имени. Для системного события — «Приложение», если событие действительно системное.

**FB-02.6.** Сопоставление ID с именем выполняется в нативном слое с действующими ACL. Изменение UI не должно открыть родителю чужие профили или весь справочник пользователей. Пароли, ключи восстановления и API-секреты в журнал не добавляются. Коды событий сохраняются для диагностики, но не являются единственной пользовательской подписью.

### Приёмка

- При двух последовательных регистрациях родителем ребёнка и второго родителя один и тот же автор отображается корректно, цели различаются.
- Старые события с существующим `actor` показывают его имя; отсутствие разрешённого имени обрабатывается нейтрально.
- Одинаковые имена различаются в подробностях; смена имени не меняет автора-ID события.
- Неподтверждённый родитель не получает имена чужих детей через журнал или прямой запрос подробностей.
- Отображение времени имеет единый формат и понятную временную зону; существующее время события не переписывается при переводе подписи.

## 5. Имена на экране входа — FB-03

### Требования с учётом решения Q-01

**FB-03.1.** В списке входа показываются отображаемое имя и роль из открытого локального списка, как разрешил заказчик. Пользователь не должен запоминать UUID для обычного входа. Внутренний выбор и аутентификация по-прежнему связаны с неизменным account ID.

**FB-03.2.** Одинаковые подписи различаются ролью и коротким суффиксом ID. После выбора профиля требуется его пароль. Подмена подписи/роли в публичном списке не даёт полномочий; авторитетные роль, профиль и связи проверяются после разблокировки.

**FB-03.3.** Публичный список содержит только согласованный минимум: ID, отображаемое имя и роль. В него не включаются школа, город, история, семейные связи, пароль и секреты. Не добавлять скрытую автодешифровку всей БД ради имён. При переименовании сохранять связь с прежним account ID.

**FB-03.4.** Создание/переименование/удаление аккаунта, восстановление backup и перенос Portable согласованно обновляют список. Нужны версия формата и восстановление после сбоя записи. Изменения метаданных не должны лишать владельца возможности войти по ID.

**FB-03.5.** После обновления старого vault, если публичных подписей ещё нет, временно показываются существующие ID; после разрешённого входа выполняется заполнение согласно принятой политике. Показ понятного объяснения обязателен; миграция не может извлечь имена из зашифрованной БД до первого успешного входа.

**FB-03.6.** Руководство, ADR и описание конфиденциальности обновляются вместе с реализацией. Разрешение заказчика уже получено; текущее указание руководства 0.1 «до авторизации только идентификаторы» заменяется описанием имён/ролей после выпуска реализованного поведения, а не заранее.

### Приёмка

- После создания профиля и перезапуска можно выбрать его по согласованной подписи, а не длинному UUID.
- Два одинаковых имени различимы; пароль одного не открывает другой профиль.
- Обновление старого хранилища, backup/restore и перенос не теряют учётки и связи.
- Публичный список не содержит данных сверх согласованного Q-01; его подмена не даёт родительских прав.

## 6. Алгебра и геометрия с 7-го класса — FB-04

### Требования

**FB-04.1.** Для новых учебных сценариев 7-го класса установить четыре самостоятельных предмета: `algebra` — «Алгебра», `geometry` — «Геометрия», `physics` — «Физика», `informatics` — «Информатика». Общая «Математика» не предлагается ученику 7-го класса как самостоятельный новый предмет.

**FB-04.2.** Каталог предметов зависит от класса и поступает из единого доменного источника. UI не поддерживает второй независимый жёстко заданный словарь. Правило для будущего расширения: `math` доступен в 1–6 классах, алгебра/геометрия — начиная с 7-го. Само расширение доступных классов не входит в этот пакет.

**FB-04.3.** Разделить каталоги тем, диагностику, рекомендации, инструменты, карту знаний, отчёты, учебные назначения и выбор ДЗ. У алгебры и геометрии могут быть разные учебники и программы. Общий дневной лимит ученика не умножается при появлении второго математического предмета.

**FB-04.4.** Текущие `math-equations`, `math-powers`, `math-fractions` классифицировать как алгебраические/необходимые базовые темы алгебры. Стабильные ID тем можно сохранить с явным предметным соответствием; переименование строковых префиксов само по себе не является обязательным и не должно разрывать историю.

**FB-04.5.** Подготовить реальный начальный каталог геометрии 7-го класса с проверенными объяснениями, упражнениями и поддерживаемыми способами проверки. Наличие пустой карточки геометрии не считается реализацией предмета. Минимальный набор для ближайшего пакета: начальные геометрические понятия и углы, смежные/вертикальные углы, треугольники и сумма углов; окончательный объём полного каталога остаётся в исходном EDU-009.

**FB-04.6.** Миграция сохраняет старые занятия, результаты и snapshots. Исходный исторический `math` и название «Математика» сохраняются как факты старого занятия; для фильтра/агрегации по новому каталогу допускается отдельная вычисленная классификация по известной теме. Неизвестные темы выводятся в «Математика — архив», без угадывания и автоматического копирования результата в геометрию.

**FB-04.7.** Не дублировать knowledge events и освоение при миграции. Повтор миграции не изменяет результат второй раз. Старые учебные назначения без однозначного предмета требуют подтверждения родителя; старое значение сохраняется до решения.

**FB-04.8.** Обновить перечень предметов в ТЗ/реестре, README, руководстве, prompts, каталогах, приёмке и тестовых данных. Геометрия — дополнение к прежнему фактическому объёму, её нельзя считать выполненной переименованием «Математики» в «Алгебру».

### Приёмка

- На главной, в предметах, ДЗ, диагностике и отчётах 7-го класса видны четыре согласованных предмета.
- Алгебра и геометрия имеют собственные непустые темы/учебные сценарии; предметные назначения независимы.
- Старые алгебраические результаты отображаются в нужном контексте без дублей и без переписывания исторических snapshots.
- Неопределённые старые записи сохраняются в архивной группе; backup до миграции восстанавливается поддерживаемым путём.

## 7. Предмет и тема домашнего задания — FB-05

### Требования

**FB-05.1.** На экране ДЗ добавить обязательный предмет из каталога для класса ученика. При входе из конкретного предмета его можно предварительно выбрать; при входе из общей навигации выбор явный. Последний использованный предмет допустим как видимая подсказка, но не скрытая отправка по умолчанию.

**FB-05.2.** До обращения за учебной проверкой пользователь подтверждает предмет и текст. Тема выбирается из этого предмета либо получает статус «не определена»; не требуется выдумывать тему ради заполнения поля. Автопредложение темы/предмета при наличии реализации должно показывать неоднозначность и давать исправление.

**FB-05.3.** Удалить скрытый fallback `topic_id="math-equations"`. В нативном контракте использовать проверенный subject ID и необязательный согласованный topic ID. Серверная команда отклоняет отсутствующий/неизвестный предмет и тему чужого предмета. Формат файла не определяет предмет без подтверждения пользователя.

**FB-05.4.** Зафиксировать предмет и тему в записи ДЗ и учебном сеансе, включать их в разрешённый контекст модели и выбор предметных инструментов. Приёмку проводить по фактическому содержимому HTTP-запроса/тестового адаптера и сохранённым данным, а не только по подписи поля.

**FB-05.5.** Не присоединять ДЗ по геометрии к активному сеансу алгебры/физики. Повторное использование сеанса допускается только при совпадении владельца, режима ДЗ и подтверждённого предметного контекста. Иначе предложить сохранить/приостановить текущий и создать отдельный сеанс с обычной проверкой лимита; скрытая смена предмета существующего занятия запрещена.

**FB-05.6.** Смена предмета в черновике сохраняет файл и текст, очищает несовместимую тему и обновляет инструменты. Ранее полученный результат остаётся связан с прежним предметом; для новой проверки требуется новая операция. Владелец/разрешения/лимиты/идемпотентность продолжают проверяться нативно.

**FB-05.7.** Для файла с заданиями разных предметов в ближайшей версии предложить разделить задания или выбрать предмет текущей проверки. Не объявлять весь документ математикой и не вводить незапрошенный скрытый многопредметный режим.

### Приёмка

- Без выбранного предмета запрос не отправляется; прямой вызов нативной команды также отклоняется.
- Геометрическое ДЗ сохраняется/обрабатывается как геометрия, физическое — как физика; соответствующий предмет передан провайдеру и инструментам.
- Активное занятие информатики не поглощает ДЗ по алгебре; пользователь получает выбор перехода, история обоих контекстов сохраняется.
- После смены предмета файл и текст остаются, несовместимая тема сбрасывается, прежний ответ не переименовывается.
- Ограничения времени и согласия не обходятся новым селектором.

## 8. Проверка Python только в информатике — FB-06

### Требования

**FB-06.1.** Блок проверки синтаксиса Python показывать только в ДЗ с подтверждённым предметом `informatics`. Пока предмет не выбран либо выбран другой, блок, редактор, кнопки и относящийся результат не отображаются в этом контексте.

**FB-06.2.** При переключении с информатики сохранить код как черновик информатики, но не включать его в запрос и оценивание другого предмета. При возвращении можно восстановить черновик. Данные другого профиля не должны попадать в этот черновик после выхода/смены пользователя.

**FB-06.3.** Нативная команда получает ID работы/сеанса и сама определяет его предмет после проверки владельца. Нельзя разрешать инструмент только по строке `subject="informatics"`, переданной UI. При вызове для другой работы возвращается понятный отказ без анализа кода.

**FB-06.4.** Существующие ограничения остаются: анализ без исполнения, без доступа к файлам/сети, вывод о синтаксисе не выдаётся за подтверждение алгоритмической правильности. Проверка синтаксиса сама по себе не отмечает тему освоенной.

### Приёмка

- При выборе алгебры, геометрии, физики и отсутствии выбора блок Python отсутствует; при выборе информатики доступен.
- Прямой вызов анализа с работой другого предмета или другого ученика отклоняется.
- Вредоносный Python-текст не исполняется; черновики не переносятся в чужой профиль/предметный запрос.

## 9. Переключение предмета на вкладке «Предметы» — FB-07

### Требования

**FB-07.1.** На вкладке «Предметы» всегда доступен локальный выбор всех предметов ученика. Предлагаемый интерфейс — видимые переключатели четырёх предметов над списком тем плюс название выбранного. Возвращаться в «Обзор» для смены не требуется.

**FB-07.2.** При переключении обновляются темы, подписи, действия диагностики и рекомендации. Выбранная тема другого предмета не остаётся скрытым параметром старта. Состояния загрузки/пустого каталога обозначены явно.

**FB-07.3.** Просмотр тем другого предмета сам по себе не завершает и не переписывает текущее занятие. Для начала нового действуют правила сохранения/паузы и запрета нескольких активных сеансов. Учебные черновики и прогресс сохраняются.

**FB-07.4.** Переключатель доступен клавиатурой, выбранное состояние различимо в светлой/тёмной/системной теме. Предметные данные берутся из того же каталога, что в ДЗ и домене.

### Приёмка

- Из открытых тем алгебры можно перейти к геометрии, физике и информатике, не покидая вкладку.
- Сразу после переключения старт/диагностика используют новый предмет, без старого topic ID.
- При активном занятии переключение каталога сохраняет его; новый старт не дублирует активное время и не теряет ответ.

## 10. Влияние на данные и совместимость

| Область | Изменение | Правило сохранности |
|---|---|---|
| Профиль | Адресные ID + названия + происхождение | Старые строки сохранять до подтверждённого сопоставления |
| Открытый список входа | Разрешены ID, отображаемое имя и роль; формат выбирает разработчик | Не хранить ключ БД/пароль; ID входа остаётся резервным способом выбора |
| Событие аудита | DTO с автором/целью, подписями и переводом кода | Не менять фактический actor; старые события не дополнять выдуманными историческими именами |
| Каталог предметов | Четыре предмета 7-го класса, единый источник | `math` поддерживать для исторических данных и будущих младших классов |

Миграции версионировать и выполнять транзакционно с проверкой повторного запуска. До преобразования данных создать резервный снимок. Изменение открытого каталога и шифротекста сохранять согласованно. Для уже выпущенных архивов определить поддерживаемый путь обновления; не объявлять новый формат совместимым без теста.

## 11. Приоритеты и последовательность

Исходный P0 не понижается. Ниже — приоритет внутри пакета исправлений, а не новая классификация всего ТЗ.

1. **Общий предметный контракт:** FB-04 (схема/соответствия), FB-05, FB-06, FB-07. Причина: ошибочный предмет меняет учебную обработку и загрязняет историю; UI и backend должны перейти согласованно. Геометрический контент — отдельная обязательная задача FB-04.5.
2. **Аудит:** FB-02 можно выполнять независимо, сохраняя правильное различие автора и цели.
3. **Классификатор:** FB-01 — закрытие исходного P0; сетевой режим разрешён, далее выбрать и проверить источник, реализовать адаптер и fallback.
4. **Вход по именам:** FB-03 — открытый список имён/ролей разрешён, далее реализовать формат и миграцию метаданных. Журнал из FB-02 отображается после авторизации и остаётся самостоятельной доработкой.
5. **Общая приёмка:** миграции, backup/restore, четыре предмета, запреты нативного слоя, обновлённое руководство и повтор пользовательских сценариев.

Сроки не назначены: уточняющие ответы получены; для оценки остаются объём геометрического банка, выбор и проверка источника классификатора, проектирование миграций. Настоящий этап фиксирует требования; реализация семи доработок ещё не выполнялась.

## 12. Готовность пакета

Каждое из семи замечаний должно иметь воспроизводимый тест и сохранённый результат; должны быть проверены положительные/отрицательные сценарии выше. Решения Q-01/Q-02 уже записаны и не требуют повторного подтверждения. Необходимо пройти миграции на копии прототипной базы и восстановление поддерживаемого старого backup. Недопустима потеря профилей, истории, программ, ключей и результатов; контекст ДЗ не должен подменяться; нативные запреты должны работать без UI. Руководство должно описывать фактически выпущенное поведение. Это критерии будущей приёмки, а не утверждение об уже пройденных проверках. Пакет не закрывает автоматически OCR, диктовку и остальные незавершённые P0 полного MVP.
