# Оценивание: строгая проверенность, диагностика темы и причины Unknown

Дата: 28.10.2026. Роль: аналитик. Основание: ответ пользователя на спорные положения EVAL-1 в [архитектурном ревью](learning-feedback-architecture-review-2026-10-27.md), [полный пакет требований](learning-feedback-requirements-2026-10-27.md).

Статус: **политика оценивания Q7 согласована ответами заказчика 28.10.2026**: порог 80% при полном проверенном покрытии, первый самостоятельный ответ, ручная проверка и апелляция связанным родителем. Темы с ошибками обязательно включаются в общую диагностику предмета. Позднее ответы Q8 заменили BANK-1: см. постановку learning-bank-requirements-2026-10-28.md.

Документ дополняет полный пакет доработок. Для оценивания он имеет приоритет над противоречащими предложениями EVAL-1, в частности разрешением подтверждения при C=2/W=0/U=1 и выдачей подтверждения по предметному тесту. Программа, рабочие данные и тестовые результаты в рамках аналитической работы не изменялись.

## 1. Принятые решения

1. Процент верных среди проверенных результатов и полнота проверки — разные показатели. 100% среди проверенных не означает полное освоение обязательного минимума.
2. Любой непроверенный обязательный компонент U запрещает полное подтверждение темы. Необработанные/неотправленные обязательные компоненты также не позволяют объявить полное покрытие.
3. Общая диагностика предмета 27+3 служит выявлению проблем и расстановке приоритетов. Даже два разных верных ответа или полный успешный предметный тест не выдают подтверждение темы.
4. Подтверждение покрытия/освоения возможно только в точечной диагностике конкретной темы. Для неё необходим заранее определённый обязательный минимум; нельзя уменьшать его после ответа ради успешного результата.
5. Unknown не является правильным или ошибочным ответом и всегда имеет причину, действие для разрешения и сохраняемый аудит.
6. Технически не принятая отправка не является ответом: её нельзя добавлять в C/W/U или количество обработанных вопросов.
7. Для полного подтверждения точечной диагностики нужны `P ≥ 80%`, `K = 100%`, `U = 0`, `S = 0` и доказанное покрытие всего обязательного минимума. Считается первый самостоятельный ответ; исправления после подсказки его не заменяют.
8. Темы с выявленными ошибками должны обязательно присутствовать в общей диагностике предмета. Порог 80% допускает подтверждение при отдельных ошибках, но не снимает обязанность повторно диагностировать ошибочные темы.
9. Связанный родитель вправе вручную проверить ответ и рассмотреть апелляцию с обязательным обоснованием и аудитом; ручной результат не выдаётся за автоматическую независимую проверку.

## 2. Единицы учёта и формулы

Нужно различать вопрос, тематический компонент вопроса и обязательный навык/элемент рубрики темы. Два вопроса на один навык не доказывают покрытие пяти разных навыков. В комбинированном задании проверка A не подтверждает B/C.

План точечной диагностики содержит версию рубрики темы, обязательные компоненты и их проверяемые задания/критерии. Сохраняются связи `question_id → topic_id → rubric_component_id`, доказательство и версия проверяющего. Нельзя подтвердить обязательный компонент только по наличию соответствующего тега у задания.

Для одного зафиксированного среза результата:

- `N` — число обязательных проверочных компонентов сохранённого плана, а не число всех попыток отправки. План обеспечивает покрытие каждого обязательного элемента рубрики; отсутствие задания для нужного элемента — неполный план, а не разрешение уменьшить минимум.
- `C` — принятые компоненты с проверенным правильным результатом; `W` — с проверенной ошибкой; `U` — принятые, но непроверенные по одной из причин раздела 4.
- `S` — обязательные компоненты, по которым ещё нет принятого ответа. Это отдельное состояние, не причина Unknown. Для текущего среза `N = C + W + U + S`.
- Процент по проверенным: `P = 100 × C / (C + W)`. Если `C+W=0`, показывать «нет проверенных результатов», а не 0% или 100%.
- Проверенное покрытие: `K = 100 × (C + W) / N` при `N>0`. Ошибка тоже проверена и входит в K, но не в C. Дополнительно показывать покрытие обязательных элементов рубрики; нельзя смешивать число вопросов с числом навыков.
- Округление применяется только для показа: 2/3 → 66,7%. Проверка полного покрытия использует целые числа/множества, а не округлённые 100%.

Эта формула применяется к одному принятому результату компонента по согласованной политике версии ответа. История повторов/исправлений не добавляет компоненты в знаменатель. Причины Unknown не дублируются: один компонент входит в U один раз; возможны основной reason_code и история уточнений.

Для предметной диагностики P/K отображаются только как результат обследованного плана. Они не означают процент освоения всего учебника и не создают TopicConfirmation.

## 3. Требования к подтверждению

| ID | Требование | Проверяемый результат |
|---|---|---|
| EVAL-01 | Разделить предметный скрининг и точечное подтверждение | Тип/цель попытки сохранены неизменно. Предметный тест выявляет проблемы/неопределённость и предлагает точечный; никакая ветка его завершения или позднего пересчёта не выдаёт новое подтверждение темы |
| EVAL-02 | Заранее определить обязательный минимум темы | Рубрика содержит перечисленные компоненты, типы вопросов и независимые критерии. Все обязательные элементы представлены заданиями; два вопроса, проверяющие один элемент из пяти, не покрывают остальные. Публикация подтверждающего теста с неполным планом запрещена |
| EVAL-03 | Подтверждать точечную диагностику при 80% и полном покрытии | Полное подтверждение невозможно при U>0, S>0 или отсутствии доказательства для хотя бы одного обязательного элемента рубрики. Необходимы K=100% и P≥80% по первым самостоятельным обязательным ответам. Сравнивать точные значения до округления; 79,96%, отображаемые как 80,0%, порог не проходят. Наличие W допускается, но запускает EVAL-09 |
| EVAL-04 | Сохранить обязательную и добровольную части раздельно | Тематический план 8+2 сохраняется. «*» можно пропустить без штрафа; звёздочка не может быть единственным способом проверить обязательный базовый компонент. Результат сложной части не закрывает пропуск обязательного компонента автоматически |
| EVAL-05 | Не подменять статус прохождения статусом проверки | Можно завершить обработанную попытку с принятыми U как «завершена, результаты частично проверены», не блокируя другую работу ученика. Подтверждения нет, пока U не разрешены. Неотвеченные обязательные вопросы дают незавершённую попытку; пропуск «*» допустим |
| EVAL-06 | Считать первый самостоятельный ответ | Хранить первый самостоятельный, исправления, подсказки, финальный ответ и способ проверки. Для P и подтверждения используется первый самостоятельный ответ на обязательный компонент. Техническая/ручная перепроверка этого же ответа уточняет его вердикт; исправление учеником после ошибки или подсказки не заменяет исходное диагностическое свидетельство |
| EVAL-07 | Пересчитывать после разрешения U воспроизводимо | Новое решение связано с прежним observation_id, ответом и revision, сохраняет старую проверку. Обновить P/K и статус атомарно и идемпотентно; не начислять повторно вопросы, время и учебные события. От предметного теста подтверждение не появляется и после пересчёта |
| EVAL-08 | Показать четыре независимых признака | В UI и отчёте раздельно: прохождение материала, процент среди проверенных, проверенное покрытие, наличие/основание подтверждения. Показывать C/W/U/S и причины U. Предыдущая оценка не стирается из-за нового неполного теста |
| EVAL-09 | Обязательно включать темы с ошибками в общую диагностику | При формировании нового предметного плана включить темы с актуальными доказанными ошибками последних тестирований/ДЗ, в том числе при уже выданном подтверждении с P≥80%. Это обязательная группа, а не рекомендационный вес; Unknown и непроверенная реплика ИИ не приравниваются к доказанной ошибке. Соблюдаются 27+3, комбинирование, минимум два разных задания по проверяемой теме и утверждённые исключения контроля. Нельзя молча отбросить ошибочную тему ради менее приоритетной; невозможность валидного плана сообщается явно |
| EVAL-10 | Дать связанному родителю проверить и рассмотреть апелляцию | Нативная проверка действующей связи с ребёнком на чтение и запись решения; автор, время, обоснование, revision ответа и scope обязательны. Решение относится к исходному первому самостоятельному ответу; не превращает подсказанное исправление в самостоятельное. Ученик не утверждает собственную проверку. Конкурирующие решения родителей проверяют revision, история не удаляется |

EVAL-11: по окончательному уточнению Q8, ИИ-only без формальной проверки требует решения связанного родителя по исходному ответу. До него обязательный компонент имеет U/awaiting_manual_review и не даёт подтверждения. После обоснованного вердикта пересчитать C/W/P/K с методом manual_parent/combined, сохраняя исходное ИИ-предложение и первый самостоятельный ответ. Одобрение подборки заданий не выполняет эту проверку. Смешанные формально и вручную проверенные компоненты допустимы; любой оставшийся U/S блокирует подтверждение.

Два разных верных вопроса **не являются достаточным основанием** и не заменяют полную рубрику. Подтверждение использует перечисленные условия EVAL-03/EVAL-11, а не статистическую уверенность по двум ответам. Согласованные 80% правильности не означают 80% покрытия: проверено должно быть 100% обязательного минимума.

Практическое следствие: 4 верных и 1 ошибочный обязательный компонент при полном покрытии позволяют точечное подтверждение, но ошибочная тема остаётся обязательной для общей диагностики. Для воспроизводимости хранить актуальные ошибки и ссылки на доказательства. Предложенная детализация жизненного цикла: снять конкретный сигнал ошибки можно по последующему проверенному самостоятельному результату по тому же компоненту либо по обоснованному пересмотру исходного вердикта; одно достижение общего порога 80% ошибку не закрывает. Уже начатый предметный тест не перестраивается: новые ошибки учитываются при следующем планировании по согласованному правилу снимка.

## 4. Причины Unknown и действия

| Код / ID | Когда возникает | Действие и статус |
|---|---|---|
| technical_error / UNK-01 | Принятый ответ есть, но проверка завершилась техническим сбоем | «Не удалось проверить по технической причине». Сохранить ответ, дать продолжить другую работу, разрешить повтор проверки того же ответа. Позже пересчитать; повтор проверки не является новой попыткой ответа |
| unsupported_format / UNK-02 | Проверяющий не поддерживает представление/тип решения, например свободный текст, рисунок или файл | Объяснить ограничение; предложить поддерживаемое представление, альтернативный вопрос с той же проверяемой целью либо ручную проверку. Не считать ошибкой ученика и не выдавать подтверждение |
| awaiting_manual_review / UNK-03 | Ответ передан на ручную проверку | Статус «ожидает проверки», привязка к проверяющему/очереди и версии ответа. До решения подтверждение не выдавать; срок и автор решения видны, автоматического превращения в правильный результат нет |
| ambiguous_result / UNK-04 | Неоднозначная проверка, частичное совпадение, спорный формат или конфликт доказательств | Сохранить доказательства/версию проверяющего; дать уточнение или апелляцию, не превращать спор в W без основания. Решение и его обоснование версионируются |
| not_accepted / UNK-05 | Отправка не прошла валидацию/не дошла до приёма | **Не U и не ответ.** Сохранить локальный черновик, показать отказ/состояние доставки, дать безопасно повторить с operation ID. Не менять C/W/U и полноту обработки |

Вместо произвольного текста «Unknown» DTO должен содержать код, безопасное пояснение, дальнейшие действия, актуальную revision, observation_id, время и метод проверки. Технические детали/секреты не публикуются. Наличие проверенного конечного числа не означает проверку неизвестного промежуточного шага.

Дополнительные инварианты:

- **Уточнение заказчика Q9:** исходная попытка и её вопрос сохраняются. Unknown разрешается перепроверкой того же исходного ответа либо обоснованным решением связанного родителя. Альтернативное задание выдаётся в новой явно запущенной попытке со связью с исходными attempt/question/observation и причиной. Результат новой попытки не заменяет наблюдение исходной, не закрывает её U и не меняет её N. Прежнее разрешение замены в текущем срезе отменено; история всех вердиктов сохраняется.
- Если ученик исправляет смысл ответа, это новая revision ответа, а не техническая перепроверка старого. Подсказки сохраняются; возможность такого ответа дать подтверждение зависит от решения раздела 8.
- Для комбинированного задания неизвестность конкретного компонента не распространяется автоматически на проверенные компоненты других тем и не устраняется их правильностью.
- Ручной вердикт связанного родителя имеет автора, время, обоснование, scope проверки и revision; способ проверки — «ручная, родитель». Подтверждение родителем факта прохождения материала **не является** проверкой правильности решения: это разные явные действия. Проверка/апелляция не даёт родителю доступа к другим детям и секретам.
- Апелляция не удаляет старый вердикт. До принятого пересмотра спорная проверка не представляется как окончательно надёжное доказательство.

## 5. Контрольные примеры

| Вид диагностики / данные | P | K | Ожидаемый результат |
|---|---|---|---|
| Точечная: N=3, C=2, W=0, U=1, S=0 | 100% | 66,7% | Проверено 2 из 3, непроверено 1; полное подтверждение отсутствует независимо от причины U |
| Точечная: N=10, C=2, W=0, U=0, S=8 | 100% | 20% | Незавершена; два правильных ответа не подтверждают остальные компоненты |
| Предметная: C=2, W=0, U=0 по теме | 100% среди проверенных | Только покрытие её компонентов в данном плане | Наблюдение для скрининга, без подтверждения темы; возможна рекомендация точечного теста |
| Точечная: N=3, C=0, W=0, U=3 | Нет процента | 0% | Частично/полностью непроверена, причины видны; нет ложного 0% правильности и нет подтверждения |
| Точечная: N=5, C=4, W=1, U=0, S=0 | 80% | 100% | Подтверждение допустимо при покрытии рубрики и первых самостоятельных ответах; тема с ошибкой обязательно включается в общую диагностику |
| Предметная: все обязательные компоненты верны и проверены | 100% | 100% собственного плана | Подтверждение темы не создаётся даже при полном успехе скрининга |
| Отправка не принята | Без изменения | Без изменения | Нет нового ответа/U; обязательный компонент остаётся S, если раньше принятого ответа не было |

Покрытие 2 из 3 даёт 66,7%, а не 100%, даже если процент правильности по проверенным 100%. При недостаточном плане относительно рубрики дополнительно показывается отсутствие обязательных элементов; метрика узкого плана не маскирует этот дефект.

## 6. Данные, архитектурные задачи и сохранение истории

- Расширить Observation/Verification: reason_code, основное состояние, revision ответа, исходный/пересмотренный вердикт, checker/rubric/policy version, автор, доказательства и scope. Для каждого обязательного элемента — стабильная связь с планом/темой и источником результата.
- Attempt хранит цель (`subject_screening`/`topic_confirmation`), снимок обязательной рубрики, компонентные связи и выбранную политику. Матрица покрытия выводится из принятых доказательств, не из итогового текста ИИ.
- TopicConfirmation разрешён только от подходящей точечной попытки; прямое создание от subject_screening блокируется доменным правилом, а не лишь скрытием кнопки UI.
- Нужны операции повторной проверки, постановки/решения ручного review связанным родителем, альтернативного вопроса и апелляции с ACL, revision и operation ID. Сетевой сбой не удерживает транзакцию и не обнуляет сохранённый ответ. Сигнал актуальной ошибки и обязательность темы в предметном плане хранят доказательство и историю изменения; подтверждение с 80% не очищает их автоматически.
- A08 архитектурного плана дополняется обязательной рубрикой и достаточным подтверждающим покрытием, A09 — различением целей и обязательным включением ошибочных тем, A10 — C/W/U/S, 80% и первым самостоятельным ответом, A11 — раздельными статусами карты, A13 — типизированными причинами и родительской ручной проверкой, A16 — приёмкой раздела 7. Роли/порог согласованы; состав банка остаётся Q8.
- При переходе с последней актуальной установленной версии сохранить старые mastery, ответы, сообщения, оригиналы и ID. Исторические попытки без рубрики/причины U не становятся доказанным подтверждением; причина старого U — `legacy_unspecified`, не выдуманный technical_error. В новой обработке такой код не использовать без миграционного основания.
- Нельзя задним числом объявить прежнее подтверждение по новому правилу действительным или удалить старую оценку. Показать как историческое свидетельство старой политики, отдельно от соответствия новой. Уже открытые попытки продолжаются по сохранённому плану/версии, новая строгая попытка запускается явно.
- Переоценка сохранённого ответа допустима только отдельным версионным действием с аудитом и разрешениями. Повторное открытие приложения не запускает скрытую массовую переоценку и не меняет исторические исходники.

## 7. Приёмка

1. Все строки раздела 5, разные причины U, нулевой знаменатель, округление близкого к 100% покрытия при остающемся непроверенном компоненте.
2. Предметный скрининг не создаёт подтверждения при успешном завершении, позднем разрешении U, повторе операции и восстановлении после сбоя. Карта сохраняет сигнал проблемы/неопределённости и отдельно предлагает точечную диагностику.
3. Точечная рубрика из 5/10 элементов не покрывается двумя ответами на один навык. Неполный/неподдерживаемый банк не публикует тест как подтверждающий полный минимум; обязательная тема не зависит только от пропущенного «*».
4. Техническая ошибка → повтор проверки → проверенный результат; ответ/время не дублируются. Поздний результат относится к точной revision исходного ответа и не перезаписывает последующее исправление; вердикт первого самостоятельного ответа можно уточнить с аудитом и пересчётом. Ответ другого vault/контекста или устаревшая проверка уже пересмотренного вердикта не публикуется.
5. Ручное ожидание, проверка/апелляция связанным родителем с обоснованием, запрет чужому родителю/ученику, отзыв связи, конфликт revision; отдельность решения о прохождении материала и вердикта по ответу. Пересмотр вердикта первого ответа не подменяет его поздним исправлением.
6. По Q9 альтернативное задание выдаётся в новой попытке с собственной квотой/планом, проверяемой целью и ссылкой на исходную проблему. В исходной попытке сохраняются вопрос, ответ, N и U до перепроверки исходного ответа или решения родителя. Успех новой попытки не заменяет старый результат; обе попытки и аудит доступны после перезапуска/restore.
7. UI и отчёт явно показывают процент, покрытие, непроверенные компоненты с причинами, неотвеченные S и статус подтверждения. Старая история, изоляция детей/vault, backup/restore, атомарность пересчёта и отмена проверены на исходниках и новом exe.
8. Граница P=80% проходит при полном покрытии, P<80% не проходит даже после округления. При P=100% и U>0 подтверждения нет. Исправление неправильного первого ответа не повышает исходный диагностический P; перепроверка самого первого ответа может изменить вердикт с аудитом.
9. Подтверждённая тема с W>0 присутствует в следующей предметной диагностике; темы с ошибками не вытесняются темами без оценки. Если не хватает мест/комбинированных заданий для выполнения обязательных условий, виден отказ формирования полного плана. Временное исключение действует по прежним правилам; начатая попытка не меняется.

## 8. Готовность

Q9 закрыт прямым ответом заказчика: исходная попытка сохраняется, Unknown разрешается перепроверкой или решением родителя, альтернативное задание даётся в новой попытке. Правило раздела 4 и сценарий 6 приведены в соответствие; дополнительные обязательные вопросы отсутствуют.

Остаточные вопросы Q7 закрыты ответами заказчика: 80% правильности при полном проверенном обязательном покрытии, первый самостоятельный ответ, ручная проверка и апелляция связанным родителем. Добавлено обязательное включение ошибочных тем в предметную диагностику. Эти решения готовы к технической декомпозиции; повторного согласования не требуют.

Q8 также закрыт: [генерируемый банк](learning-bank-requirements-2026-10-28.md) охватывает все темы, требует шагов, допускает новые фото, сохраняет историю и ротирует усвоенные вопросы. Полные учебники не хранятся, метаданные/темы/история сохраняются. Родитель утверждает каждую новую подборку; при ИИ-only без формальной проверки отдельно решает по ответу ученика. Эти два согласования не взаимозаменяемы. Первый самостоятельный ответ не подменяется исправленным фото. Программа, миграция рабочих данных и публикация не выполнялись.
