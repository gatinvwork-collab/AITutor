# Учебный процесс: техническая постановка разработчику

Дата: 28.10.2026. Роль: архитектор. Статус: **Q1–Q9 согласованы; постановка A01–A20 готова к разработке**. Это постановка разработки, не отчёт о выполнении. Новые пороги качества ИИ и производительности не объявляются уже измеренными.

Приоритет требований: [банк/STEP/ROT/HIST](learning-bank-requirements-2026-10-28.md) и [оценивание EVAL/UNK](learning-assessment-requirements-2026-10-28.md) уточняют [основной пакет](learning-feedback-requirements-2026-10-27.md). [Архитектурное заключение](learning-feedback-architecture-review-2026-10-27.md) фиксирует согласованные решения; Q9 разрешил конфликт замены вопроса после Unknown. Старый ограниченный BANK-1 не является границей поставки.

## 1. Границы реализации

Сохранить Python / PySide6 / Qt WebEngine / QWebChannel, локальную семейную базу и Portable. UI работает через разрешённые нативные команды; сетевой поиск, ИИ, SQLite, ACL и секреты находятся в Python. Замена стека и удалённый собственный backend для этого пакета не нужны.

База перехода по репозиторию: 0.4.1, схема 3, AEAD-контейнер формата 1. Целевое проектное решение: схема 4 и новый формат учебных агрегатов, при неизменном формате криптоконтейнера и `.aitbackup`. Если к началу выпуска последняя установленная версия окажется иной, вход миграции и фикстуры обновить до неё; номер будущего релиза этим документом не назначается.

Основные модули: `curricula` — источники/книги/темы; `question_bank` — генерации/подборки; `assessment` — планы/рубрики/результаты; `verification` — предметные проверки; `review` — родительские решения; `jobs` — сетевые задачи; `migrations` — совместимость. Названия проектные. `Service` координирует транзакции и доступ; не переносить всё в `answer()` и `providers.py`.

## 2. Обязательные доменные правила

### 2.1. Программа и область поддержки

- Разделить учебник/издание, назначение ученику, школьную программу, каталог тем, текущую тему, подтверждённое прохождение и оценку освоения.
- Автоматический путь: поиск открытого источника → загрузка → постобработка ИИ → кандидат с источником/версией → предпросмотр → публикация родителем. Ученик готовит предложение; родитель также может создать/исправить программу сам. Публикация автоматически полученного кандидата родителем — сохранённое проектное допущение из заключения, согласованная обязанность предпросмотра не отменяется.
- Нет источника/сети/согласия — сохранить школу, реквизиты и черновик; дать ручной путь. Для неизвестного курса использовать применимую федеральную программу как явно обозначенный резервный ориентир к началу класса. Не считать всю программу текущего класса пройденной.
- Ученик предлагает пройденные темы, родитель подтверждает конкретные topic ID. Импорт/текущая тема сами не дают этого факта. Отмена и изменение — новые решения с аудитом.
- Хранить реквизиты, структурированные темы, URL/идентификатор источника, версию, дату, рубрики, сгенерированные задания и историю. Полные тексты/сканы учебников не превращать в постоянный продуктовый архив. Для обработки использовать ограниченную временную область без постоянного plaintext-кэша; учебные оригиналы ученика сохраняются зашифрованными.
- Матрица выпуска охватывает все темы явно выбранной программы/издания; перечень поддержанных версий фиксируется в поставке. Выбор нового издания в эксплуатации запускает проверку его матрицы и подготовку банка, а не автоматически наследует статус полной поддержки. Каталог можно показать сразу, готовность проверки показывать отдельно.

### 2.2. Генерируемый банк и четыре вида родительских решений

Основной банк генерируется, статические фикстуры допустимы для тестов и legacy. Вопрос неизменяемой версии содержит условие, уровень/«*», тему, навыки рубрики, критерии компонентов, пошаговый эталон, источники, модель/версию промпта и отчёты проверок.

Стадии: `generated → ai_reviewed → validated → pending_parent → approved/rejected`. Ошибка/конфликт — `invalid/stale`. Содержательная ИИ-проверка выполняется отдельной стадией; одинаковые ответы генератора и проверяющего не считаются доказательством независимой формальной проверки. Проверяются полнота условия, решаемость, согласованность шагов/эталона, рубрика/возраст, структура, единицы, дубли; при наличии формального метода он применяется дополнительно.

Подборка — сохранённый список точных question ID/version, рубрик, уровней и источников для ребёнка, включая разрешённый резерв. Каждая новая/существенно изменённая подборка требует решения связанного родителя. До решения вопросы не выдаются ученику; эталон в ученический DTO до ответа не включается. Выбор неизменённого утверждённого резерва не является новой генерацией и не требует повторного одобрения.

Отдельные объекты решений, не взаимозаменяемые:

1. Публикация программы/учебника и соответствий тем.
2. Подтверждение факта прохождения тем.
3. `collection_approval`: допуск конкретной подборки/version.
4. `answer_review`: вердикт по конкретному исходному ответу/компоненту; обязательны обоснование, scope и revision.

Везде проверять действующую связь с учеником при чтении и непосредственно перед записью. Конфликт двух родителей — ошибка revision с перечитыванием. Одобрение подборки не проверяет будущие ответы.

### 2.3. План и оценка

Сохранять неизменяемый исходный план, purpose, область, рубрики, источники приоритета, квоты, выбранные вопросы/варианты, версии проверки/политики и разрешённый резерв до выдачи. Не строить новую попытку при каждом открытии экрана. Адаптация допустима только по заранее сохранённым правилам/вариантам без потери квот и покрытия; выбор варианта фиксировать до выдачи.

Точечная диагностика — 8 обязательных + 2 «*» для первой реализации. Предметная — ровно 27 + 3; комбинированный вопрос физически один. Два разных вопроса по теме — требование планового покрытия предметного скрининга, а не правило подтверждения. Полную обязательную рубрику точечной диагностики покрывать обязательной частью; если в 8 вопросах покрыть её невозможно, план не публиковать как готовый. Не переносить обязательный навык только в «*».

В предметном плане все актуальные темы с доказанными ошибками — обязательная группа после применения временных исключений. Только затем пройденные без оценки и остальные допустимые темы. При переполнении обязательной группы искать допустимое комбинирование; если полного плана нет, сообщить невозможность, а не молча отбросить обязательную тему. Добор: разные допустимые задания текущих тем, затем подходящий подтверждённый прошлогодний банк; выдуманного прошлого курса нет.

Ошибка — сигнал с topic/rubric ID, observation ID, датой и методом доказательства. Сигнал закрывается последующим проверенным самостоятельным успехом по тому же компоненту либо обоснованным пересмотром исходного вердикта, с аудитом. Общие 80% его не закрывают. Новые ошибки не перестраивают начатый тест.

Единицы данных различать:

- `question_id` — физический вопрос;
- `assessment_component_id` — обязательное проверочное действие сохранённого плана, имеет одну тему, критерий и связи с элементами рубрики;
- `rubric_element_id` — обязательный навык темы. В одном вопросе могут проверяться несколько разных навыков одной темы; это не несколько разных вопросов.

Для обязательных компонентов `N = C + W + U + S`. C — проверено верно; W — проверенная ошибка; U — принятый, но непроверенный ответ; S — нет принятого ответа. `P = 100*C/(C+W)`, при нулевом знаменателе процент отсутствует. `K = 100*(C+W)/N`, при N=0 план невалиден. Для покрытия рубрики дополнительно считать множество навыков с достаточными доказательствами, не только компонентный процент.

Использовать первый самостоятельный ответ. Подсказки/исправления хранятся, не подменяют его. Если самостоятельного свидетельства нет, не придумывать его: компонент не может дать самостоятельное подтверждение. Перепроверка того же исходного ответа меняет его вердикт версионно и атомарно, не число ответов. Точная проверка порога: `5*C >= 4*(C+W)`; округлять только отображение.

**TopicConfirmation создаётся исключительно от topic_confirmation**, если P≥80%, K=100%, U=S=0, все обязательные навыки доказательно покрыты и соблюдена самостоятельность. W допускается и сохраняет ошибочные темы обязательными для следующего скрининга. `subject_screening` никогда не создаёт подтверждение, включая поздний ручной пересчёт. Цель и политику нельзя менять после старта.

Все обязательные вопросы обработаны и все «*» отвечены/явно пропущены — попытка может завершиться. При U результат «частично проверен», подтверждения нет; S даёт незавершённую попытку. Завершённость и проверенность — отдельные поля. Новая работа доступна во время ожидания review с соблюдением дневного лимита.

**Согласованный Q9:** после принятого ответа вопрос исходной попытки не заменяется. Unknown разрешается перепроверкой того же первого самостоятельного ответа или обоснованным решением родителя; вердикт меняется версионно с атомарным пересчётом и аудитом. Альтернативное задание включается только в новую явно запущенную попытку с отдельным ID и собственными квотами, утверждённой подборкой и правилами самостоятельности. Сохранить ссылки на исходные attempt/question/observation и причину альтернативы. Результат новой попытки не переносится в старую, не закрывает её U и не меняет N; исходный U меняется только после проверки исходного ответа. Сохранённые до выдачи правила выбора вариантов остаются допустимыми.

### 2.4. Unknown и методы проверки

Методы: `formal`, `ai`, `manual_parent`, `combined`. Хранить отдельно предложенный ИИ-вердикт и принятый проверенный результат. AI-only обязательного компонента даёт `U/awaiting_manual_review`, не C/W для подтверждения или доказанного сигнала ошибки. Родитель проверяет именно исходный ответ; после обоснованного решения допустим C/W с методом manual_parent/combined. Формальная проверка конечного числа не доказывает все шаги и не покрывает автоматически другие компоненты.

Причины U: technical_error, unsupported_format, awaiting_manual_review, ambiguous_result. `not_accepted` — ошибка приёма, а не U; остаётся S, ранее принятый ответ не теряется. DTO результата: observation ID, answer revision, code, безопасное пояснение, allowed_actions, scope, method, checker version, timestamp. В миграции допустим `legacy_unspecified`; для новых проверок его не использовать.

Формальные проверяющие используют ограниченную грамматику, точные дроби и единицы. Ввод не исполняется. Для семантического анализа алгоритма текущего AST-проверяющего недостаточно: нужен отдельный предметный анализ. Исполнение кода ученика не включать без отдельного изолированного механизма; полный охват автоматизированного разбора можно строить через ИИ-анализ с честным способом проверки и обязательным родительским review там, где нет формального метода.

### 2.5. Ротация

Считать успех точной версии вопроса для конкретного ребёнка в завершённых диагностических попытках обоих типов: один успех на `(student, question_revision, attempt)`. Предпросмотр, ДЗ, чат, повтор ответа и повтор проверки не являются отдельными тестами. Все компоненты вопроса должны быть верны, самостоятельны и проверены, необходимые шаги представлены. Для «*» нужен реальный ответ.

Три успеха накопительно, без требования подряд: вопрос исключается из следующих назначений этому ученику, заменяется новым содержательно отличным аналогом той же цели/уровня. Новый вопрос получает новый ID и собственный счётчик. Ротация не подтверждает тему, не очищает иные ошибки и не меняет начатую попытку.

При отмене успеха пересчитать счётчик; если он стал <3, вопрос снова доступен для будущих планов, изменение eligibility аудируется. Уже сохранённые планы остаются прежними. Это техническая политика ROT-05. Дефицит утверждённых замен видим; не возвращать усвоенный вопрос скрытно. Размер резерва — версионная инженерная настройка с проверкой матрицы, не произвольный заказчиком заданный порог.

### 2.6. ДЗ, OCR, дополнительные фото и журнал

Работа одна, у неё версии условия/решения и много неизменяемых originals. Каждое фото: предпросмотр → OCR → редактирование/формулы → подтверждение revision → отправка. Несколько страниц до первой отправки составляют один зафиксированный ответ. Новое фото после замечания — следующая версия; не заменяет первое самостоятельное решение. Более читаемую копию считать перепроверкой только при доказанной неизменности содержания с аудитом; при сомнении — новая revision.

Проверять необходимые шаги и альтернативные верные способы. Верное полное решение не запускает обязательный допрос. Верный итог без шагов — запрос недостающих данных, а не автоматическая ошибка. Ошибка шага — адресный запрос пояснения; неизвестность OCR — не ошибка ученика.

Разделить намерения `check` и `hint`. Диалог продолжается в той же работе с ссылками на версии, фото и шаги. Хранить фактически отправленный учебный контекст, запросы/ответы ИИ, модель/провайдер, версии промптов, usage и статусы. Секреты/Authorization/OAuth не сохраняются в журнал вызова. Полный локальный журнал не сокращается вслед за сетевым контекстом.

Markdown/TeX — единый локальный безопасный рендерер для текущего и исторического текста, редактор и ресурсы в Portable; исходник не изменяется. HTML/скрипты и внешние ресурсы запрещены; сложные/ошибочные формулы имеют безопасный fallback. Оба дизайна, три темы, клавиатура и копирование обязательны.

## 3. Хранение и транзакционные границы

Сохранить legacy `records`, новые критичные связи вынести в нормализованные таблицы. Названия проектные; окончательный SQL с типами/индексами входит в A01. Версии immutable, изменяемые указатели и решения защищены revision. Все новые данные остаются внутри зашифрованного контейнера; перенос вложений наружу не входит в эту поставку.

| Группа таблиц | Ключевые связи/ограничения |
|---|---|
| edition_revision, assignment_revision, curriculum_revision, source | Stable ID + revision; назначение → student/users и edition; один актуальный указатель на student/subject; URL/источник и статус происхождения |
| topic, curriculum_topic, topic_mapping, study_request, study_decision | Тема не идентифицируется названием; FK к конкретной версии каталога; решения прохождения → request/student/parent и список topic ID; отдельно текущая тема |
| rubric_revision, rubric_element, question_revision, question_component | Версия рубрики → перечисленные навыки; component → question + topic + criterion; отдельная таблица связи с rubric_element, без ложных FK внутрь JSON |
| collection_revision, collection_item, collection_decision | Immutable состав; unique(collection, question_revision); решение → точная collection revision/student/parent |
| assessment_attempt, attempt_slot, slot_component, attempt_event | FK к student, версии rubric/policy/collection; purpose CHECK(topic_confirmation/subject_screening/legacy); unique(attempt, position), отсутствие повторной версии/эквивалентного задания в попытке проверяет домен |
| answer_revision, verification_revision, observation_current | FK к slot component и точной answer revision; одно выбранное текущее наблюдение на assessment_component; история проверок append-only; pointer обновляется с expected_revision |
| topic_confirmation, error_signal, control_exclusion | Confirmation → подходящая attempt/result revision; error → component/observation; исправление результата пересматривает основание подтверждения/сигнала с аудитом, не удаляет старый факт |
| question_success, question_eligibility | UNIQUE(student, question_revision, attempt); счётчик вычисляем/кэш проверяем; eligibility scoped к student |
| homework_revision, original, recognition_revision, dialogue_turn, ai_call | Original → student/work/answer revision; исходные байты неизменны; OCR/text confirmed revision; call → разрешённый снимок контекста без секретов |
| review_request, review_decision, background_job, operation, event | Типизированная цель, FK и revision; UNIQUE(student, operation_id), fingerprint; jobs scoped к vault/context/student; аудит не зависит от текущего имени |

Сущности ученика имеют owner/parent chain для ACL и удаления. Общие каталоги не удаляются вместе с одним учеником; персональные назначения, подборки, review, фото, сообщения, success, операции и задачи удаляются штатной политикой удаления профиля. Существующее `DELETE FROM records WHERE owner` не охватит новые таблицы — обновить обязательно.

Атомарные публикации:

1. Принять ответ: answer revision + фиксация первого самостоятельного + S→U/pending + operation result. Сохранение ответа не зависит от сети. Только после успешного checkpoint запускать проверку.
2. Опубликовать проверку/review: verification + current observation + C/W/U/S + P/K + error signals + подходящее confirmation + успех/eligibility + аудит + operation. Поздний вердикт исходного ответа допустим и при наличии исправления: не перезаписывает новый текст, оценивает именно зафиксированный первый ответ.
3. Допустить подборку: решение родителя и approved pointer одной транзакцией, после сверки состава/revision.
4. Изменить прохождение/исключение: решение + действующее состояние + уведомления/аудит. Начатые планы не обновляются.

Уникальность операции задаётся пользователем/контекстом команды и ID; повтор с другим fingerprint — conflict. Отправка, OCR, AI-call, результат проверки, ответ ученика и физический вопрос — разные счётчики; не дублировать время/usage при повторной доставке. Завершившийся внешний вызов не гарантирует сохранение при аварии: хранить попытки вызова и неизвестный транспортный исход, не обещать exactly-once у провайдера без его поддержки.

Типизированные ошибки: authentication, forbidden, conflict, consent_required, source_unavailable, insufficient_bank, mandatory_topics_overflow, collection_pending, unsupported_format, time_limit, cancelled, stale_result, capacity, migration. Не передавать внутренние пути/секреты в error details.

`NativeWorker` сейчас однопоточный, `Service.dispatch` держит lock во время сети. Добавить отдельный ограниченный executor для сетевых jobs, сохранив один путь записи SQLite. Фазы: коротко сохранить намерение → сеть/парсинг по минимальному snapshot вне SQL/Service lock → сериализованная публикация. Сетевой worker не читает live SQLite. На публикации проверить vault, generation/context, owner, связь/согласия, input revision и отмену; несоответствие даёт stale/cancelled.

Не блокировать ручное сохранение из-за нормализации/генерации. Jobs имеют pending/running/succeeded/failed/cancelled/stale, конечные повторы, ограниченную очередь и видимые причины. После запуска незавершённая работа восстанавливается как проверяемая задача, не бесконечная скрытая пересылка. Logout/restore/delete отменяют персональные задачи; восстановление vault никогда не получает результат старого контекста.

Загрузчик проверяет HTTPS, DNS/адреса каждого redirect, запрещает private/loopback/link-local и чтение локальных файлов, ограничивает время/объём/распаковку/типы. Школьная ссылка и ответ ИИ — недоверенные данные. Лимиты импорта сохранить: 8 МиБ/файл, 30 000 символов текста, PDF до 30 страниц, изображение до 25 Мп; несколько фото не должны обходить лимит текста отправляемого решения. При превышении — явная разбивка/отказ, без молчаливого усечения. Оригиналы сохраняются; состояние capacity не обходит 256 МиБ контейнера.

Изображение в облако — отдельное явное разрешение по умолчанию false; прежнее allow_documents означает прежнюю передачу подтверждённого текста. Отзыв проверять перед каждым upload/chat и публикацией; TLS не отключать. GC-F и жизненный цикл временных удалённых файлов реализовать единым адаптером. Источник открытый, но персональные школьные/семейные реквизиты не добавлять в ИИ-контекст без необходимости и разрешений.

## 5. Миграция и сохранение истории

1. Зафиксировать исходный exe/version/hash. Создать синтетическую fixture реальной последней версии, включая оба родительских профиля, детей, секрет/согласия, оригиналы, паузу, ДЗ, архив, usage и backup.
2. Закрыть старый процесс и проверить installation/vault lock. Рекомендовать отдельную полную старую Portable-папку для возврата; встроенная миграция сама создаёт зашифрованный pre-migration snapshot.
3. После корректного unlock и проверки формата до модификации сохранить точные исходные байты контейнера и проверить backup. При отказе/нехватке места миграцию не начинать. Рассчитать место/память для старого контейнера, копии и нового временного снимка; замерить пиковые расходы.
4. Выполнить схему 3→4; для 1/2 — весь маршрут 1/2→3→4 в staging/памяти с единой финальной публикацией. Верифицировать integrity/FK и ограничения версии. Migration marker, данные и envelope записываются единым штатным atomic checkpoint. Сеть/ИИ/генерация во время миграции запрещены.
5. Сохранить все users/links/records/kinds и исторические значения. Обёртки, vault/account IDs и attachment derivation/AAD не меняются. Секреты GigaChat PERS и прежние согласия сохраняются с прежним смыслом; новое разрешение фото false.
6. Старый каталог/задания — legacy snapshot; не удалять ради генерации. Старые session/knowledge/event/mastery и program_snapshot не переоцениваются. Legacy-only поля можно проецировать в новые структуры через адаптер с сохранением исходных ID и provenance.
7. Старым ответам не придумывать рубрику, checker, шаги, AI-request, reason U, first-independent или success count. Unknown происхождение маркировать legacy_unspecified. Автоматически не создавать TopicConfirmation, родительские одобрения новых подборок, прохождение или исключения.
8. Ротацию нового механизма считать только по достаточным достоверным наблюдениям. Legacy-счётчики correct/total не доказывают три разных самостоятельных успешных теста точного вопроса; по умолчанию backfill не делать, неизвестность отдельно.
9. Незавершённый legacy-тест можно продолжить старым обработчиком по старому снимку либо явно архивировать незавершённым и начать новый; не дописывать 30 новых вопросов. Время выключения/обновления не начисляется. Черновики/оригиналы не теряются.
10. Запрет постоянного хранения полной книги не удаляет старые пользовательские оригиналы. Реальное удаление по этому основанию требует отдельного указания и не входит в миграцию. Старые verified=False отображаются как «независимая проверка не выполнена», текст модели не переписывается.
11. После публикации — закрытие/повторный вход, доступ всех ролей, новая запись, новое backup и restore. Старый exe отвергает схему 4, возврат — только к полной отдельной старой папке, обратного слияния новых данных нет.

Backup формата 1 остаётся совместимым как упаковка полного контейнера. Обновить restore/Transfer для схемы 4 и маршрута старых схем, изолированного staging, отказа непустому назначению и очистки при сбое. Все новые фото/таблицы/решения входят в контейнер: нельзя упаковать только legacy records. Сравнивать до/после исторические значения, связи и хеши расшифрованных originals; рандомизированный ciphertext не обязан совпадать.

Сбой backup/DDL/шифрования/записи/fsync/replace/повторного запуска оставляет валидный старый либо новый контейнер. Проверять восстановление RAM при провале checkpoint, отсутствие частичного миграционного маркера и идемпотентность повторной миграции. Реальное отключение питания отдельно от fault injection не выдавать за уже пройденное испытание.

## 7. Приёмка и условия выпуска

До разработки полного объёма провести четыре технических пробы: генерация/шаги на репрезентативных темах всех четырёх предметов; OCR печатного/рукописного решения; поиск точного издания/программы; замеры RAM/размера/времени checkpoint с многими фото и журналами. Это не сокращает выпуск до BANK-1. Если какая-либо тема системно не поддерживается, полный заявленный выпуск заблокирован; ручной review не скрывает отсутствующий автоматизированный разбор темы.

Для каждой темы coverage matrix фиксирует источник/рубрику, типы решений, формальный и ИИ-методы, сценарии альтернативных верных путей, негативные/ambiguous/unsupported примеры и ожидаемые scope. Критерий: проходят принятые эталоны без ложного подтверждения и без системного пробела по целой теме. Численные универсальные гарантии точности модели не заявлять; результаты корпуса и известные ограничения приложить к поставке. Новые модели/промпты требуют регрессии матрицы.

Обязательные сквозные проверки:

1. Тема 8+2, предмет 27+3, 0/1/2/3/13/14/15/16/много тем; разные компоненты/навыки; mandatory topics overflow; исключения; approved reserve; отсутствие ИИ/источника. Валидный полный план либо понятный отказ, не фиктивная полнота.
2. Точечные C=4/W=1/N=5 и 80%; 79,96% не проходит; C=2/U=1 даёт P=100% и K=66,7%, без подтверждения; S>0 и N=0; subject_screening не подтверждает ни при каком пересчёте. Ошибочный родительский вердикт может быть пересмотрен с сохранением аудита и оснований.
3. Генерация→ИИ review→автопроверки→collection approval→выдача; revision состава, pending/rejected/stale, два родителя; скрытые эталоны не попадают в ученический snapshot. Выбор approved reserve допускается без нового решения, изменение содержания требует решения.
4. AI-only→U/manual queue→review исходного ответа→атомарный пересчёт; mixed formal/manual; отмена/апелляция и поздние результаты; доступ после отзыва связи. Review коллекции и факта прохождения не закрывает U.
5. Три разных завершённых теста, повтор операции, один тест с тремя ответами, U/подсказка, комбинированный вопрос с одним W, два ребёнка, последующий пересмотр успеха. Усвоенный question не выбирается без допустимого пересмотра; начало новой попытки не меняет старую.
6. Фото до/после замечания, несколько страниц, OCR-ошибка, period/mixed fractions и формулы, ручная правка, подтверждение revision, сохранение черновика при сбое, лимит/отмена/cleanup. Первый самостоятельный ответ неизменен, technical rescan не подменяет смысл.
7. Полное правильное решение без лишнего опроса, правильный итог без шагов с уточнением, адресная ошибка шага, неподдерживаемое/неоднозначное решение; эталоны 145а–в/146а–г и все темы матрицы. Не доказывать рубрику совпавшим числом.
8. История всех ответов/ИИ-запросов/фото после перезапуска, миграции и restore; ключи и Authorization отсутствуют в журнале; документы/ИИ/XSS не исполняют HTML/код; оба дизайна × три темы и офлайн-render.
9. Миграция последней реальной версии, схемы 1/2/3, checksum originals, counts/values всех видов, пароли/recovery/GigaChat PERS, новая запись/backup/restore; сбои критичных стадий и возврат отдельной копией. Legacy не получает новых рубрик/успехов/подтверждений.
10. Регрессия дневного лимита/idle/монотонного времени, меню/фокуса, ограниченной очереди, ACL и удаления; замеры с ростом журналов/фото и близко к 256 МиБ. До capacity отказ сохраняет рабочий контейнер; историю ради освобождения места не удалять.

11. Q9: принятый Unknown остаётся в исходной попытке без замены вопроса/N. Перепроверка или родительский review того же исходного ответа меняет его вердикт с аудитом и пересчётом без повторного начисления. Поставка: исходники, новый Portable exe с хешем/манифестом, актуальная coverage matrix и корпус, ADR/SQL/контракты, протокол исходников и exe, список реальных ИИ/OCR/источниковых проверок отдельно от mocks, инструкция обновления/возврата и известные ограничения. Данные заказчика и публикация не изменяются в рамках архитектурной постановки.
