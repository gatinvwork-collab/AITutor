# План приёмки MVP

Статус всех сценариев: **не выполнялся**. Это реестр для подготовки тестов, а не протокол успешной приёмки. Источник: раздел 16 ТЗ MVP 1.0 от 25.10.2026. Уточнения ниже не заменяют исходные ожидаемые результаты.

## Общие тестовые данные и правила

Использовать только синтетические профили: P1/P2 — подтверждённые родители S1; P3 связан только с S2; S0 без родителя. Родительские связи не выводятся из похожих имён. Создать отдельный профиль без связи с семейными данными для отрицательных проверок.

Каталог: три предмета 7-го класса, подтверждённая и неподтверждённая школа, две версии программы/учебника. Материалы: текстовая задача с верным/ошибочным решением, чёткое/нечёткое фото, рукопись, PDF, DOCX, таблица/график/чертёж/формула, безопасный и вредоносный пример кода. Вредоносный код не запускать вне доказанно изолированной среды.

Для каждого запуска сохранить: ID теста и варианта, commit/checksum сборки, окружение, fixture version, предусловия, точные шаги, ожидаемый и фактический результат, статус, безопасные доказательства, ссылку на дефект. Тест считается passed только при совпадении фактического результата; отсутствие ключа/оборудования — blocked. После появления реализации каждый сценарий получает подробный исполняемый или ручной тест-кейс.

## Обязательные дополнительные проверки

- Для AT-19–22 проверить весь набор HW-001, не только один удачный файл. Включить большие/повреждённые файлы и инструкции prompt injection.
- Для AUTH/ACL проверить каждую защищённую команду прямым IPC-вызовом, отозванные связи, одновременное изменение настроек двумя родителями и удаление профиля.
- Для backup проверить архив без дополнительного шифрования: исходная БД/вложения всё равно зашифрованы. Проверить неверный ключ, свободное место, архивные пути, остановку во время замены и копию после смены пароля.
- Для DB/NFR проверить сбой записи, миграцию, восстановление checkpoint, двойную отправку, отмену и поздний ответ модели; отсутствие потери завершённых записей.
- Для Portable проверить read-only папку, отсутствие runtime и расположение управляемых WebView-файлов. Учесть только явно документированные неизбежные системные исключения.
- Для производительности записать конфигурацию ПК и замеры всех показателей раздела 17.3; пороги согласовать по результатам PoC до итоговой приёмки.

## Форма протокола

```text
Test ID / variant:
Build commit / checksum:
Environment / fixture version:
Preconditions:
Steps:
Expected:
Actual:
Status: not_run | passed | failed | blocked
Evidence (без секретов):
Defect / remaining limitation:
Date / tester:
```

Пилот разрешается после выполнения определения готовности из ТЗ, технической приёмки и закрытия вопросов использования материалов/данных детей. Педагогическая эффективность не выводится из количества passed-тестов.
