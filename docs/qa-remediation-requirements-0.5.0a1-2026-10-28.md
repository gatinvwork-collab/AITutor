## 3. QA-050-01: изоляция жизненного цикла попыток

### Воспроизведение и локализация

Ученик начинает A, обрабатывает восемь обязательных вопросов и отвечает/явно пропускает два «*», сохраняет A приостановленной. Затем начинает B и завершает A из её карточки. По QA B остаётся active в базе, но `Service.assessment_active=None`: на исходниках 30 секунд не начислены, на exe значение seconds не изменилось за 6,5 секунды. Это не ошибка округления минут в UI.

В `LearningEngine.change_status()` поле `assessment_active` и общие `last_tick/last_action` изменяются безусловно в `save()` для любой попытки. `Service.tick()` выбирает обработчик по указателю, поэтому переключение состояния A затрагивает B.

### Требования

| ID | Требование | Критерий приёмки |
|---|---|---|
| TIME-050-01 | Разрешить завершение подготовленной приостановленной A при активной B без выключения B | Завершена только A; B остаётся активной, её указатель согласован с БД. Не вводить новый запрет такого завершения вместо исправления без отдельного продуктового решения |
| TIME-050-02 | Менять активный указатель и базовые отметки только для соответствующей попытки | Finish/pause A не сбрасывает/переназначает B и не обновляет её last_action как будто ученик выполнил учебное действие. Допустим обычный корректный checkpoint времени B до операции; он не должен терять или дважды начислять интервал |
| TIME-050-03 | Сохранить взаимное исключение занятий и ограничения | Не более одной активной учебной работы по действующим правилам; старые занятия, новые попытки и ДЗ не обходят дневной предел, grace и idle из-за перехода состояния исторической попытки |
| TIME-050-04 | Атомарно сохранять состояние попытки и runtime-контекст | Отказ записи не оставляет указатель, статусы и счётчики в разных состояниях. Повтор operation_id возвращает прежний результат; stale revision/чужой ID не меняют A/B и время сверх штатного checkpoint |
| TIME-050-05 | Не делать скрытый ремонт исторического времени | Исправить дальнейший учёт. Пропущенное время старых сессий не вычислять как разницу настенных часов: активность/idle неизвестны. Если обнаружен конфликт runtime/БД, обработать явно без начисления неопределённого простоя |
| TIME-050-06 | Сохранить безопасное восстановление после перезапуска | Активные на момент аварии занятия/попытки восстанавливаются по действующему правилу явного продолжения. Закрытое приложение не начисляет время; перенос/restore не оживляет таймер другой попытки |

Приёмка: на управляемых монотонных часах A paused → B active → finish A → +30 секунд → tick; у B прирост ровно 30 секунд при отсутствии idle/лимитной отсечки, дневной расход увеличен ровно на тот же интервал. A не получает время B. На exe дождаться более одного периода фонового учёта и проверить секунды/дневной расход, а не только округлённые минуты. Дополнительно проверить B близко к idle/дневному пределу, ошибку записи, повтор операции, finish без B, ошибочную revision, роли и legacy-занятия.

## 4. QA-050-02: полный смысл короткого диалога ДЗ

### Воспроизведение и локализация

В одной подтверждённой работе ученик отправляет `QA_CONTEXT: объясни вычитание пяти`, получает ответ, затем пишет `Поясни мой предыдущий вопрос подробнее`. Во втором фактически переданном запросе предыдущего вопроса нет. Он сохраняется в локальном журнале первого вызова: потерян контекст для модели, а не запись на диске. Порог 30 000 символов не достигнут.

В `work_check()` цикл по `prior[-4:]` добавляет только `call['response']` как assistant, без соответствующей пользовательской реплики. Локальная история запроса/ответа сама по себе не гарантирует правильный следующий запрос.

### Требования

| ID | Требование | Критерий приёмки |
|---|---|---|
| DLG-050-01 | Строить контекст из реально состоявшихся упорядоченных реплик | Во втором коротком уточнении есть первое уточнение user, ответ assistant и текущий user; роли/порядок корректны. Последовательные assistant без породивших их доступных user-реплик не заменяют диалог |
| DLG-050-02 | Избежать рекурсивного дублирования снимков | Не вставлять в следующий запрос целиком все `messages` каждого прошлого вызова: это размножает system, условие и ранние реплики. Каждая логическая реплика включена ровно один раз; исходное решение и правила передаются в определённом месте |
| DLG-050-03 | Собирать контекст только одной разрешённой работы и нужных версий | Проверять student/work/vault и revision. Предыдущие версии решения могут использоваться только с явной маркировкой, не выдаются за текущую. Новая подтверждённая revision не теряет историю; запоздалый ответ помечен как относящийся к старой версии, а не применён к новой |
| DLG-050-04 | Соблюдать лимит без молчаливой потери коротких уточнений | 2–4 короткие пары check/hint/follow_up помещаются при имеющемся бюджете. Для длинного диалога возможен явный отказ до внешнего запроса с сохранением черновика/истории либо документированное сокращение целых пар с видимым признаком. Нельзя оставить только ответ модели без смыслового контекста. Лимит не повышать молча |
| DLG-050-05 | Различать успешные, ошибочные, отменённые и stale-вызовы | Техническая ошибка не вставляется как учебный ответ assistant. Принятый вопрос ученика не исчезает; его статус и допустимость включения в следующий контекст явны. Повтор operation_id не размножает вопрос/ответ, время и usage; новая реплика — новая операция |
| DLG-050-06 | Сохранять фактический контекст и полный журнал | Для каждого нового вызова сохраняются действительно отправленные сообщения, revision, ответ/статус и доступные метаданные без ключей/токенов. Старые сохранённые запросы остаются неизменными: нельзя задним числом добавить туда то, что модели не отправлялось. После перезапуска короткий диалог продолжается по журналу |

Приёмка проверяет **payload**, а не похожесть/качество словесного ответа ИИ. Первое уточнение QA_CONTEXT и его ответ присутствуют во втором запросе; текущее уточнение — один раз. Отдельно проверить 2–4 пары, check→follow_up, hint→follow_up, новую revision текста/фото, перезапуск, отмену/ошибку, превышение бюджета, одновременные работы, смену ученика/restore с совпадающими ID. Полный локальный журнал сохраняется даже при сокращении сетевого контекста.

## 5. QA-050-03: единый предмет от перехода до записи

### Воспроизведение и локализация

Новый вход ученика → «Предметы» → «Информатика» → «Проверить ДЗ по этому предмету» → при необходимости загрузить программы/работы → создать работу. На exe зафиксировано requested=informatics, selected=algebra, created=algebra. При старом выборе может подставляться другой предмет.

`subject-homework` записывает `state.hwSubject`, но новый `learningPage()` использует `state.learnSubject` или первый предмет; `homeworkPage()` уже перенаправляет на новый экран. Это несовпадение двух моделей состояния, не подтверждённый дефект нативного справочника предметов.

### Требования

| ID | Требование | Критерий приёмки |
|---|---|---|
| SUB-050-01 | Передавать предмет перехода новому экрану единым способом | Предмет кнопки имеет приоритет над старым выбором экрана. Для каждого из четырёх предметов requested=selected=subject в команде создания=subject сохранённой записи |
| SUB-050-02 | Сохранить выбор при асинхронной загрузке данных | Первый показ/загрузка/refresh не подменяют предмет на первый элемент или прежний выбор. Если пользователь успел явно изменить предмет, старый ответ загрузки не откатывает новое действие; незнакомый/недоступный subject требует выбора, не молчаливой алгебры |
| SUB-050-03 | Согласовать предмет, тему и форму | Темы/программа/название кнопки соответствуют предмету; несоответствующая старая тема не переносится. Черновики/существующие работы не переписываются при переходе. Если смена предмета затрагивает несохранённый ввод, сохранять его либо запросить явное решение |
| SUB-050-04 | Валидировать создаваемую работу нативно | Не полагаться только на надпись select: проверять действующий subject и принадлежность темы/программы, владельца и revision, где применимо. Python-действия доступны для работы по информатике, не для ошибочно названной карточки |
| SUB-050-05 | Не изменять предмет старых работ автоматически | Исправление UI влияет на новые операции. Существующие algebra-работы не становятся informatics по догадке из текста или последнего маршрута; возможный пользовательский ремонт выполняется явно по правилам раздела 6 |

Приёмка: все четыре предмета; до/после первой загрузки; прежний другой learnSubject; повторный переход из нового предмета; refresh; logout/login; быстрый выбор во время загрузки; отсутствие каталога/невалидный subject. На exe проверить фактическую новую запись и профиль ученика, не только выбранный пункт DOM. Для информатики дополнительно проверить Python-действие и отсутствие его у остальных предметов.

## 6. Обновление и сохранение истории

### Два обязательных исходных состояния

1. **Последняя опубликованная 0.4.1, схема 3 → исправленная предварительная версия.** Сохранить действующий путь 3→4, backup перед изменением и прежнюю семантику данных. Этот путь не отменяется тем, что ошибки найдены в 0.5.0a1.
2. **Уже использованная 0.5.0a1, схема 4 → версия исправлений.** Сохранить новые программы/подборки/согласования, попытки, компоненты, review, работы, версии, фото/OCR и журналы. Не создавать новую семью и не требовать повторного ввода утраченных из-за обновления данных.

Фактическую версию/хеш установленного exe и схему фиксировать перед переходом; номер нового релиза не равен номеру схемы. Для локального исправления runtime/UI/сборки контекста повышение SQL-схемы само по себе не требуется. Если вводятся новые постоянные сущности/поля для реплик или маркеров восстановления, описать версионное преобразование/совместимость и проверять его идемпотентность; не обещать схему 4 без оценки окончательной реализации.

Старые неправильные результаты не объявляются исправленными только потому, что новая версия исправно работает.

### Условия закрытия и ограничения приёмки

Каждый QA-050-ID закрывается только при ссылке на требования, тест ожидаемого поведения и успешный прогон нового exe. Закрытие всех трёх означает приёмку **этого пакета исправлений**, а не полной 0.5.0/MVP. Полная приёмка A01–A20 остаётся неподтверждённой до выполнения остальных требований и непроверенных условий из независимого QA.

В README/инструкции не называть предварительную сборку полным релизом. Указать исходную/исправленную версии, сценарий обновления и ограничения: старое потерянное время не рассчитано заново, прежние ИИ-запросы не переписаны, предмет старых работ не изменён автоматически. Исторические QA-реестры/протоколы остаются неизменёнными; добавить новый протокол исправлений с трассировкой.

## 8. Достаточность данных

Версия, идентификация exe, предусловия, шаги, факты, локализация и доказательства уже есть в репозитории. Дополнительные обязательные вопросы заказчику для этого пакета не требуются. Выбранное поведение — завершение A без остановки B, сохранение осмысленного диалога и точного предмета новой работы — следует из действующих требований; новые бизнес-правила не вводятся. До выполнения доработок все три дефекта открыты, полная приёмка не подтверждена.
