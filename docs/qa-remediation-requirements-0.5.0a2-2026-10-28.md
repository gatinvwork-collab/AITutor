## 3. QA-050-04: отказ checkpoint при автопаузе

### Воспроизведение и техническое основание

Синтетическая семья, активная диагностика, свободный лимит. Продвинуть управляемые монотонные часы на 181 секунду без учебных действий, на один `app.tick()` подменить `store.save()` отказом `OSError`. После ожидаемого исключения восстановить запись и вызвать tick ещё раз.

По QA после ошибки SQL-статус active, runtime `assessment_active=None`; после следующего tick попытка по-прежнему active, seconds и дневной расход 0. Ожидаемый повтор после восстановления записи должен начислить допустимые 180 секунд и оформить паузу, а не потерять попытку. История ответов в этом сценарии не удалялась.

В `Learning.tick()` runtime-указатель обнуляется внутри SQL-транзакции до успешного сохранения. База при отказе откатывается, runtime — нет; `Service.tick()` больше не выбирает обработчик этой попытки. В `mutate()` уже есть восстановление runtime при исключении, но оно не защищает этот путь tick. Это подтверждённая локализация, а конкретный способ исправления выбирает разработчик.

### Требования

| ID | Требование | Критерий приёмки |
|---|---|---|
| AUTO-050-01 | Публиковать переход runtime согласованно с checkpoint | После отказа статус БД, assessment_active, last_tick/last_action, seconds и daily соответствуют предыдущему согласованному состоянию. Нельзя оставить сохранённую active-попытку без работающего учёта. Runtime можно публиковать после commit либо полностью откатывать при ошибке |
| AUTO-050-02 | Повторно обработать автопаузу после восстановления записи | В контрольном сценарии следующий успешный tick учитывает ровно 180 допустимых секунд, ставит paused и очищает указатель только после сохранения. Дневной расход увеличивается на тот же интервал; дополнительные tick после паузы ничего не начисляют |
| AUTO-050-03 | Сохранить границы idle и лимита/grace | Проверить обе причины автопаузы: idle 180 с и окончание допустимого времени limit+900 с по действующим правилам. Не начислять весь простой или время сверх grace, не сбрасывать last_action как новое действие ученика. Исправление не изменяет сами лимиты |
| AUTO-050-04 | Обработать отказ обычного tick и повторные отказы | Не только ветвь автопаузы: сохранение активного checkpoint тоже атомарно. Серия отказов не двигает успешную временную базу и не дублирует расход; после восстановления считается только допустимый интервал от последнего сохранённого checkpoint |
| AUTO-050-05 | Не допускать обхода ограничений и молчаливого успеха | При несохранённом checkpoint не разрешать новое конфликтующее занятие/ДЗ за счёт потерянного указателя. Отказ видим как ошибка сохранения с возможностью повторить после устранения причины; не сообщать «приостановлено/сохранено», пока запись не состоялась. Техническая диагностика не содержит ответов, ключей и персональных данных |
| AUTO-050-06 | Сохранить изоляцию активной и исторической работы | Регрессия QA-050-01 обязательна: finish исторической A не меняет runtime B. Неверный ID/владелец/revision, повтор операции, pause/resume/finish и переход между legacy-занятием, диагностикой и ДЗ не создают две активные работы |
| AUTO-050-07 | Восстанавливаться безопасно после закрытия процесса | Сохранить правило явного продолжения после аварийного завершения. Не начислять время выключенного приложения и неизвестные старые интервалы. Согласованность текущего процесса после отказа не подменять вычислением времени по настенным часам |

**Уровни доказательств:** существующий дефект воспроизведён на нативном Service с инъекцией отказа; отказ записи на готовом exe ещё не вводился. Повторная нативная fault-проверка обязательна. Для бинарной приёмки выполнить контролируемый отказ только на отдельной синтетической копии, с проверкой восстановления; не заполнять рабочий диск и не портить реальную `app-data`. Если такой бинарный fault-тест не выполнен, обозначить именно эту границу непроверенной, а не считать её пройденной по обычному smoke.

## 4. QA-050-05: режим действия теряется при уточнении

### Воспроизведение и техническое основание

Три отдельные работы по алгебре с одинаковым подтверждённым решением `3x+5=20; 3x=15; x=5`, одной revision и без истории. Поочерёдно отправить check, hint, follow_up с одинаковым непустым уточнением «Поясни второй шаг», соблюдая правила паузы между работами. Сравнить фактические массивы messages.

В a2 три массива messages одинаковы, хотя локальные body.intent различаются. В `work_messages()` выражение `follow_up.strip() if follow_up else INTENTS[intent]` заменяет инструкцию режима текстом уточнения; базовый JSON также не содержит текущего intent. Общая фраза `intent=hint` в system одинакова для трёх запросов и не передаёт выбор пользователя. Доказан дефект контракта payload, а не то, что любая живая модель обязательно даст неверную подсказку.

### Требования

| ID | Требование | Критерий приёмки |
|---|---|---|
| INT-050-01 | Всегда передавать текущий выбранный режим в модель | В фактически отправленном messages явно и однозначно представлен check/hint/follow_up и соответствующая инструкция. Это содержимое запроса, а не только локальная metadata или поля задачи |
| INT-050-02 | Передавать уточнение дополнительно к режиму | Непустой follow_up дополняет выбранное действие, не заменяет его. При hint модель получает «дать подсказку» и сам вопрос ученика; при check — проверку полного решения с уточнением; при follow_up — продолжение обсуждения |
| INT-050-03 | Разделить режим как управление и текст как данные | Не выводить режим из слов ученика и не переключать его скрытно по наличию уточнения. Пустая/пробельная строка не превращает current в пустой запрос: выбранный режим остаётся. Невалидное значение intent отклонять до провайдера, без молчаливого default |
| INT-050-04 | Согласовать UI, задачу, payload и журнал | Режим на момент отправки, snapshot задачи, body.intent и переданный модели режим совпадают. Последующее переключение select не меняет уже отправленный запрос. Для каждого вызова хранится действительно переданный payload; старые журналы не переписываются |
| INT-050-05 | Сохранить исправленный смысл истории a2 | Не потерять прежние user/assistant-пары, порядок и ссылку на revision работы. Не размножать вложенные снимки. Текущий режим имеет приоритет над режимами исторических вызовов; старый hint не должен делать следующий check подсказкой. OCR/ошибки/отмена не становятся учебными ответами |
| INT-050-06 | Проверять лимит после сборки полного запроса | Дополнительная инструкция входит в текущий бюджет 30 000 символов. При превышении — действующий явный отказ до отправки, с сохранением истории/черновика, без усечения. Повтор operation_id не создаёт дубликат сообщения/расхода, конфликт содержимого не меняет прежний вызов |

Матрица приёмки: `check/hint/follow_up × пустое/пробельное/непустое уточнение`, отдельно несколько последовательных разных режимов в одной работе, версия решения, повтор/отмена/stale, перезапуск и legacy-журнал a1/a2. Проверять конкретный **семантически соответствующий intent и инструкцию в payload**, не только `messages != messages` — случайные ID или времена тоже могли бы сделать массивы разными, не исправив дефект. Ответ тестовой модели может быть детерминированным; живой платный запрос для доказательства передачи режима не требуется.

Уточнение не изменяет цель работы и предмет; полнота/пошаговость проверки, подсказки и первый самостоятельный ответ учитываются по Q7/Q8. Передача hint не даёт права автоматически подтверждать знания или выдавать полный ответ как проверенный.

В README опубликованная 0.4.1 и последняя предварительная a2 — разные статусы; не называть a2 полностью принятым релизом.

| ID | Требование | Критерий приёмки |
|---|---|---|
| MIG-A2-01 | Зафиксировать источник и подготовить возврат | Версия/хеш exe, схема и формат контейнера известны; приложение закрыто; сохранена отдельная полная Portable-папка. Проверены место/права/блокировки. Миграционные пробы используют отдельные синтетические копии |
| MIG-A2-02 | Не менять формат данных без необходимости | Исправления runtime и payload сами по себе не требуют массовой перезаписи истории или новой SQL-схемы. Ожидается сохранение схемы 4, формата AEAD/backup 1 при отсутствии структурных изменений; если они понадобятся — отдельная версия и идемпотентная миграция с backup |
| MIG-A2-03 | Сохранить весь пользовательский контекст | Vault/account IDs, пароли/recovery, связи, PERS/секреты, согласия, программы/темы, подборки и их утверждения, ответы/оценки/первые самостоятельные решения, ручные review, ротация, фото/OCR, операции, журналы и дневной расход сохранены. Разрешение фотографий не включается автоматически |
| MIG-A2-04 | Не реконструировать неизвестное прошлое время | Уже потерянные интервалы из a2 не начислять задним числом по настенным часам. Не обнулять существующий расход и не делать незаметную переоценку попыток. Исправление гарантирует дальнейшую согласованную обработку и повтор checkpoint в текущем процессе, но не выдумывает старую активность |
| MIG-A2-05 | Сохранить фактический старый запрос и выбранное намерение отдельно | В старой записи a2 body.intent может существовать, хотя в messages он отсутствовал. Сохранить оба факта: нельзя дописать intent в прежний payload и утверждать, что его получила модель. | MIG-A2-06 | Сохранить безопасное восстановление и ранее исправленные данные | Не менять автоматически предмет старых работ или результаты ИИ. Явная исправленная копия, её новый ID/неподтверждённый текст/provenance и старый оригинал сохраняются. После перезапуска — явное продолжение, без начисления выключенного времени. После обновления проверить вход, старую историю/фото, продолжение диалога с корректными режимами, новую диагностику/таймер, сохранение и повторное открытие. Для вложений сравнить расшифрованный оригинал побайтно на тестовых данных; весь зашифрованный контейнер после легитимного изменения не обязан иметь старый SHA256.
