## 1. Вердикт и фактическая база

Использовать существующий Python / Qt WebEngine / QWebChannel, `Service`/`Learning`, сериализованные записи SQLite и отдельные сетевые jobs. Новый backend, замена стека и второй независимый учебный движок не нужны. Новый пакет — продолжение A01–A20, а не повторная реализация уже принятого a4.

Последняя документированная и принятая база — **0.5.0a4, схема 4, AEAD 1, backup 1**. Хеш a4 из релизного документа: `42fa4d34dd43702a3593c2bdc79a4f52863269b5abd7efc2570b7833f8d22183`; соответствие фактически запущенному exe проверяется перед воспроизведением/обновлением. Прежнее исходное основание 0.4.1 не является основным источником нового перехода, но его путь обновления сохраняется.

Совместимость по областям:

| Область | Вывод и изменение границ |
|---|---|
| Источники | Нужен специализированный приёмник книги/УМК и модель их соответствия. Нельзя просто повысить лимиты `sources.extract()` и ДЗ |

Подтверждение только точечное при ≥80% и полной проверенности без U/S; предметный скрининг подтверждения не создаёт. Q9 сохраняется: вопрос после принятого ответа не заменяется в исходной попытке; альтернатива — отдельная попытка.

## 2. Подтверждённые разрывы и границы доказательств

1. `sources.fetch()` по умолчанию ограничен 8 МиБ, `extract()` — PDF до 30 страниц/30 000 символов. Файл книги 26 941 252 байта, 257 страниц и без текстового слоя из анализа не может пройти этот путь. Это достаточное объяснение несовместимости пути импорта, но не доказательство ответа сети приложения по указанным URL.
2. В `Learning.launch()` стадия source_import добавляет извлечённый текст непосредственно перед отправкой, но в call-журнале сохраняет исходные messages и хеш source_text. По нему нельзя восстановить фактически отправленный payload. Нужна точка наблюдения после сборки и очистки разрешённого контекста непосредственно перед запросом.
3. В `finish()` исключения публикации попадают в обработчик, который обновляет job/call как stale. Поэтому ошибка схемы/покрытия и настоящий конфликт revision теряют различие. В `NetworkJobs.work()` ошибка callback публикации также может привести к повторному вызову publish из общего except. Конечный результат должен фиксироваться один раз по attempt token.
4. Генерация запрашивает все темы одним вызовом и принимает 10–300 вопросов, а проверяет минимум два вопроса на обязательный навык. Это не доказывает достаточность для точечных планов 8+2 с резервом. Отказ при масштабе 40 основных пунктов ожидаем как риск, но точная причина пяти пользовательских ошибок не доказана.
5. `learningPage()` содержит программы, банк, работы, запросы и задачи вместе. В `ui/app.js` глобальный `syncBusyState()` выключает большинство полей при `inFlight`; `rpc()` имеет тайм-аут 200 секунд, transfer — 30 минут. Эти значения не являются согласованными NFR и не объясняют сами по себе, какая операция мешает вводу пароля.
6. В `learning_schema.py` у темы есть position/title, но нет явной иерархии глава/§/пункт, сегмента PDF и применимости УМК. Нельзя поместить всё в title и затем вычислять порядок сортировкой строк.
7. Обычный `Diagnostics` — выключенный по умолчанию performance JSONL без содержимого, с ограничением 2 МиБ. Добавление туда учебных payload нарушило бы назначение и границу приватности существующего журнала.

## 3. Согласованные уточнения Q10/Q11

Порядок «следующая по оглавлению» и точный способ developer-входа уже согласованы и повторно не спрашиваются. Неизвестные причины UI/генерации устанавливаются воспроизведением, а не дополнительным опросом об исходниках.

### Q10. Нативная матрица доступа по будущим темам

**Решение заказчика:** по будущим темам разрешены самостоятельное изучение и проверка ДЗ. Точечная диагностика доступна после открытия темы либо подтверждения её прохождения родителем.

Прежнее предложение ограничить самостоятельное изучение темами current/studied/next не принято в этой части. Оглавление и заявление прохождения доступны для любой темы. Нативный допуск к точечной диагностике проверяет `opened OR studied_approved`, а не наличие отметки studied_requested. Проверка ДЗ/изучение будущей темы сами не открывают точечный тест и не подтверждают освоение. Обязательные ошибочные темы предметного скрининга и временные исключения контроля сохраняют прежние правила; UI-блокировка точечного теста не удаляет обязательную тему из предметного плана.

### Q11. Необязательный пункт между основными темами

**Решение заказчика:** автоматически открывать следующую основную тему, оставляя дополнительный материал доступным по желанию. Пропуск не означает освоения.

После подтверждения текущей темы алгоритм идёт вперёд по оглавлению, пропускает один или несколько optional-пунктов как обязательные барьеры и открывает ближайшую следующую основную тему. Не требовать кнопки пропуска или проверки optional для этого перехода. Дополнительные пункты остаются в оглавлении с признаком необязательности и доступны для добровольного изучения/ДЗ; точечная диагностика подчиняется отдельному допуску Q10. Автоматический обход optional не создаёт studied_approved, TopicConfirmation или успех вопроса. Если далее только optional либо конец книги, основная тема не выдумывается.

Q10/Q11 закрыты. Дополнительных обязательных вопросов для постановки нет. Порядок основных тем остаётся порядком оглавления, не поиском первой ранее пропущенной темы.

## 4. Проектирование источников и рубрик

### 4.1. Специализированный приёмник

Добавить отдельный `SourceImport` use case, не вызывать импорт ДЗ для полной книги. Локальный выбор — только нативный file dialog с непрозрачным handle для UI; веб-форма не передаёт произвольный путь. Сетевой путь использует существующие проверки публичного HTTPS, DNS pinning/каждого redirect и TLS.

Инженерные стартовые ограничения для новой реализации: 64 МиБ на источник, 600 PDF-страниц, discovery по первым 6 и последним 12 страницам, не более 4 страниц в одной OCR-партии, до 20 выбранных страниц на один явно подтверждённый этап извлечения. Один ИИ-текстовый фрагмент до 30 000 символов; OCR-изображение до 25 Мп и действующих ограничений адаптера. Это **проектные параметры**, не ранее утверждённые заказчиком числа. Они принимают аналитический пример 26,9 МиБ/257 страниц, но не разрешают обработку всей книги. Для дополнительных страниц — явное продолжение с прогрессом и бюджетом, не скрытое снятие лимита. До выпуска проверить/скорректировать по ресурсным измерениям с сохранением ограничения ДЗ 8 МиБ/30 страниц/30 000 символов.

Сетевой timeout: connect/read до 15 секунд, общий бюджет получения до 120 секунд, не более 5 переходов; все чтения bounded, отмена проверяется между чанками. Не выдавать 403 за «темы не найдены». Не сохранять подписанную query-строку как безопасную публичную ссылку в trace: оставить очищенный URL/идентификатор и хеш запроса.

Фазы: `accepted → metadata → discovery → text_or_ocr → hierarchy → method_match → skills → preview`. Неудача УМК не отменяет пригодное оглавление книги. Отдельно возможны awaiting_pages/awaiting_consent/manual_required, failed/cancelled/stale.

Большой PDF парсить/рендерить в ограниченном дочернем процессе с ограничением времени/памяти и контролируемым IPC; принудительная остановка не завершает приложение и не меняет SQLite. Нельзя доверять только метаданным размера страницы: контролировать фактические размеры растра/число объектов/выходные байты. Проектный предел worker: 512 МиБ RAM и 60 секунд на партию с последующим замером на целевом ПК. Процесс не получает ключ vault и право публикации, только нужные входные байты/выбранные страницы.

Проверить текстовый слой и его качество на выбранных страницах. Нулевой текст → OCR выбранных страниц, не пустой каталог. Discovery использует bookmarks/заголовки и ограниченную выборку начала/конца; числа 255–257 для книги — эталон теста, не production-константа. При неуспехе дать предпросмотр миниатюр/явный выбор страниц и ручной путь.

Полный скачанный файл существует только на время задачи в RAM либо в зашифрованном временном контейнере; plaintext whole-book cache не создаётся. Для worker допустима передача ограниченных байтов через IPC, без постоянного PDF на диске. Очистка при завершении/отмене/старте после аварии. Локальный оригинал Downloads не меняется и не удаляется. В vault остаются хеш/размер/реквизиты/страничное provenance, структурированные темы и допустимые фрагментные доказательства, а не вся книга.

### 4.2. Идентичность и совместимость

Источник имеет тип book/methodical/school_program/federal, source ID/hash, edition, ISBN при известности, segments и статус происхождения. В одном PDF возможны несколько документов, классов и разная печатная нумерация. Для каждой ссылки на материал хранить pdf_page и printed_label независимо, не применять глобальный offset.

Каталог — дерево с node ID, parent, kind(chapter/paragraph/topic), order, label/number, optional и source location. Учебные цели связывать с leaf-topic, главы/§ — навигационные группы. Для книги из анализа ожидается 6 глав/15 §/46 листовых пунктов, 6 дополнительных. Ответы/указатель/исторические сведения/упражнения и материал других классов не превращаются в обычные темы. Структура не подтверждает навыки автоматически.

`MethodCompatibility(book_revision, method_revision)` имеет compatible/incompatible/unknown, поля сравнения и доказательства/причины, algorithm version и проверенные source segments. Год сам по себе не критерий. Для пары 2023/2017 отрицательное решение обосновать различиями структуры/тем/адресации. Unknown не становится compatible по умолчанию. При публикации точной программы родитель видит решение и происхождение навыков; он не может одной кнопкой превратить доказанно несовместимый УМК в проверенный источник.

Навыки извлекать из применимого УМК; отсутствующие — ИИ по точному leaf-topic/классу/ограниченному контексту с пометкой ai_proposed. Раздельные provenance на уровне навыка и рубрики. Извлечённый кандидат не становится утверждённой программой, прохождением или одобренной подборкой. Перенос в форму сверяет draft revision; ручные изменения показываются как конфликт/merge preview, а не молча затираются.

## 5. Каталог, доступ и экраны

Единый нативный DTO `subject_context(student, subject)` выдаёт актуальную assignment/curriculum revision, дерево, flat ordered leaves, current, запросы/подтверждённое прохождение, confirmation, exclusion и `allowed_actions/reasons`. UI не вычисляет ACL и политику по индексу массива. Проверка той же политики обязательна в старте изучения/точечного теста и иных выбранных по Q10 действиях; прямой IPC не обходит disabled карточки.

После подтверждения current вычислить ближайший следующий основной лист принятого оглавления, обходя optional-пункты без обязательного действия ученика. Открытие не равно автоматическому изменению current; сохраняется явный выбор текущей темы. При отсутствии следующего основного листа показать завершение основной последовательности, сохраняя optional для добровольной работы. Доступность — производная от актуальных фактов и policy version; её изменение не меняет mastery. Пересмотр confirmation/current/издания пересчитывает новые действия, но не переписывает начатую попытку. В DTO различать `opened` для допуска к точечному тесту и `can_study/can_check_homework`: будущая тема может разрешать изучение/ДЗ без открытия точечного теста.

| Состояние темы | Изучение и ДЗ | Точечная диагностика |
|---|---|---|
| Будущая, не открыта, прохождение не утверждено | Доступны | Недоступна; причина и предложение заявить прохождение |
| Заявление прохождения pending/rejected, тема не открыта | Доступны | Недоступна; запрос не заменяет решение родителя |
| Открыта либо прохождение утверждено родителем | Доступны | Доступна при остальных штатных условиях: банк/подборка, права, время |
| Дополнительный пункт, обойдённый последовательностью | Доступны по желанию | Только при отдельном `opened OR studied_approved`; обход сам не считается открытием/освоением |
| Контроль временно исключён | Добровольные действия сохраняются | Добровольно при `opened OR studied_approved`; автоматическое назначение исключено |

Просмотр оглавления и заявление доступны для любой темы. Все действия остаются в границах прежних ACL, согласий, дневного лимита и требований к подготовленному банку; матрица не разрешает доступ к чужим данным или автоматическое подтверждение.

Все изученные/ранние темы сохраняют собственные факты; не создавать пройденность по позиции. Legacy-попытки продолжаются своим обработчиком, статические темы доступны в архиве; активный маршрут не подменяет динамическое назначение статическим fallback. Неподтверждённое сопоставление новых листьев не копирует одну старую оценку на каждый.

Общие компоненты: SubjectContext, TopicTree, SourceImportPreview, RequestsList, BankPreparation, AttemptsList, HomeworkEditor, JobsPanel. Композиция экранов различается:

- Родитель `program`: источники/издания/программа, кандидат/редакция, прохождение и решения.
- Родитель `learning`: текущее состояние, банк/подборки, попытки/работы, review и jobs; настройки книги открываются ссылкой в program.
- Ученик `homework`: собственный список/редактор работ, фото/OCR/check/hint/follow_up; без административных форм.
- Ученик `learning/subjects`: единый каталог, current/заявления, карта и допустимые действия.

Ключ черновика: vault/context + student + subject + object ID + base revision. Навигация не меняет ребёнка/предмет скрытно; logout/restore очищает память DOM/черновики/доступ. Сохранить доступность Python только для работ по информатике и существующий корректный выбор предмета.

## 6. Оркестрация генерации и jobs

До сети `PreparationPlan` фиксирует curriculum/rubric/model/policy revision, цели, mandatory topics/skills, 8+2/27+3, требуемые комбинации, ротацию/резерв, численность и бюджет партий. Не умножать слепо два вопроса на тему. Проверить осуществимость будущих планов по distinct question и skill coverage. 400 вопросов при 40 основных темах — пример масштаба, а не константа для любой программы.

Разделить preparation aggregate и партии; существующий предел 300 на один вызов не становится пределом всей подготовки. Партию ограничивать модельным контекстом/ответом и временем, хранить stage artifacts и issues. После партий дедуплицировать также между партиями, пересчитать полноту и сохраняемый резерв. Дополнять только дефицит; предложенное начальное ограничение — один исходный вызов и максимум два явных repair на партию, с показом бюджета и возможностью прекратить. Это параметр реализации; никаких бесконечных оплачиваемых retry.

Частичный корректный результат — candidate, не approved. Ремонт условия/эталона/компонента создаёт новую версию, повторный ИИ-review и автоматические проверки. Лишь полная собранная подборка становится pending_parent; неизменный одобренный резерв можно использовать по правилам Q8. Поздняя правка программы не перепубликует старую генерацию.

Терминальное состояние:

- succeeded — результат опубликован целиком;
- failed — ошибка сети/структуры/ИИ-review/покрытия/фиксации с точным stage и code;
- stale — доказанное несовпадение входной revision/контекста/согласий с текущей;
- cancelled — подтверждённая отмена без публикации результата.

Для request_cancel хранить промежуточный признак, не объявлять задачу cancelled до остановки/терминализации. Unknown транспортный исход не выдавать за гарантированную отмену удалённого запроса. Если отмена и валидация состязаются, победившая атомарная терминализация фиксирует причину и проигравшее событие в истории.

`status`, `stage`, `error_code`, safe_message, validation_path, retryable, expected/received/missing и correlation IDs раздельны. Отказ ИИ-review — review_rejected с issues, не unsupported_format HTTP/JSON. Реальный finish_reason/truncation не теряется; обрезанный ответ не публикуется.

NetworkJobs вызывает финализатор один раз; ошибки финализатора обрабатываются отдельно от worker, не повторной публикацией. Транзакция доменных записей и terminal job state атомарна. Артефакты стадий допустимо сохранять до этой транзакции без частичного допуска подборки. При ошибке диска нельзя гарантировать запись новой ошибки в тот же повреждённый storage: сохранить рабочий контейнер, сообщить отказ, при следующем входе отметить незавершённый job как interrupted с известным фактом без выдуманного finished time. Ошибка диагностики не меняет педагогический результат.

## 7. Developer-доступ и защищённый trace

Сохранить буквально 10 нажатий по «Идентификатор входа» и точное `god`. Счётчик, диалог, отмена и сброс на переходе — часть UI; решение выдаёт нативный слой с session/context-bound флагом, не доверяет JS boolean. Один клик учитывается один раз. Это барьер случайного доступа, не новая криптографическая роль; не заменять другой схемой пароля.

Developer-unlock и trace_enabled — разные состояния. После 10/god настройки открыты, но запись выключена. Logout/restore/смена профиля/перезапуск закрывают доступ и выключают запись. До обычного входа доступны только неперсональные настройки/состояние; ключ vault не выдаётся по god. После входа просмотр/экспорт дополнительно ограничены обычными ACL текущего профиля: ученик видит свои разрешённые сведения, родитель — связанных детей. Эталоны будущих заданий, system prompts с эталонами и родительские решения не раскрываются ученику через trace. Полный защищённый внутренний журнал не равен неограниченному DTO просмотра. Это применение уже действующих прав, а не изменение способа developer-входа.

Отдельный модуль ContentTrace, не расширение plaintext performance JSONL. Хранение — зашифрованные сегменты в `app-data/logs/learning-trace`, с domain-separated ключом vault и AAD(vault,trace_session,segment,format). Учебный learning_calls остаётся в vault и backup; очищать/ротировать trace не означает удалять историю. Внешние trace-сегменты диагностические, не обязательная часть учебного backup, старые сегменты при restore другого vault не открываются и не появляются в его списке.

Проектные пределы: до 4 МиБ на сегмент, 20 МиБ на trace-session, 100 МиБ на vault и 7 суток хранения; ограниченная очередь записи 256 событий. Переполнение останавливает подробную запись с видимым `trace_incomplete`, без молчаливого усечения события и без остановки учебной операции. Содержимое больших ответов хранится в ограниченных чанках одного события либо событие явно неполное; trace не выдаёт урезанную запись за полный payload. Значения — инженерная настройка, не прежнее согласование заказчика.

Точки записи: фактическая сборка разрешённого messages/images/parameters → транспортная отправка → полученный response/status/usage/finish_reason → parsing/review/validation → publish/terminal. Разделить transport attempt и domain operation. Для images хранить безопасные метаданные/hash/страницы и разрешённые учебные данные; целая книга/её сканы не попадают в trace/export. Исходные разрешённые текстовые фрагменты source_import фиксируются как фактически отправленные, не подменяются хешем. Не накапливать полный текст книги через бессистемный лог всех страниц: собирать только фрагменты, действительно отобранные bounded importer для конкретной цели.

Секреты удаляются до записи: Authorization/Basic/Bearer, API/OAuth/recovery/пароли, credential URLs; секретные команды register/login/recover/save_provider полностью исключаются из content capture, остаются безопасные этапы/длительности. Не логировать произвольные HTTP-заголовки или exception repr. Санитайзер учитывает активные известные секреты в ответе провайдера и вложенных полях; проверяется тестовыми canary. Диагностика блокировки пароля фиксирует только control ID/operation/stage/focus/busy/time, никогда value/clipboard.

Просмотр/экспорт — явные нативные команды, текущий ACL, developer session и выбранные IDs. Экспорт через нативный save dialog, очищенный набор разрешённых записей, manifest периода/полноты/причин пропусков и предупреждение о персональном учебном содержимом. Никакой автоматической отправки третьим лицам. Очистка удаляет только разрешённые диагностические сегменты внутри проверенной директории, без UI-пути к произвольному файлу. Ошибка записи/экспорта не ломает учебный save.

## 8. Операции UI и первый физический ввод

Первое действие — воспроизведение SEL29-A/B на фактическом exe с версией/хешем, Windows/DPI, окном/скроллом/темой и активной командой. Синтетическая семья/тестовый пароль; записываются pointer/focus/change и сохранённый эффект без содержимого пароля. Различать видимость busy и причину его существования. Нельзя считать жалобу устранённой DOM-установкой value.

Заменить глобальный `inFlight` как источник отключения всех контролов на registry операций: operation ID, context epoch, route revision, target IDs, conflict scopes, started/deadline, cancel_requested и terminal state. Повтор конфликтующей мутации блокируется, просмотр и независимые черновики работают. Число запросов по-прежнему ограничено; это не разрешение параллельных записей SQLite.

Login запускается только submit/Enter. Начальная status-загрузка не блокирует неопределённо поле пароля. При ошибке/timeout UI восстанавливает разрешённые поля, но не предполагает, что серверная мутация отменена: предложить проверку статуса/идемпотентный повтор, исходная native операция остаётся владельцем результата до установления исхода. Поздний ответ не снимает busy другой операции и не меняет экран другого context epoch.

Инженерные бюджеты: read-only status/overview UI deadline 15 секунд, изменение локальных данных/login 30 секунд, принятие сетевого job 15 секунд; долгая работа наблюдается по job ID, не удерживает глобальную блокировку. Реальную отмену/сетевой timeout контролирует нативный слой. Transfer сохраняет свой отдельный длительный сценарий. При медленном KDF/большой базе сроки проверяются измерениями; истечение UI deadline не запускает повтор мутации с новым operation ID.

Рендерить устойчивый shell и ключевые формы; patch только затронутых областей. Не заменять active select/textarea и не передвигать layout при pointer-down/раскрытом выборе. Polling не ставит jobs очередью, коалесцируется и пропускается при занятости. Старое disabled по ACL/валидации не превращается в enabled после снятия busy; вычислять effective availability из причин, а не безусловным `disabled=false` по набору элементов.

## 9. Данные и миграция

### Решение о версии

Предлагается **SQL-схема 5**: требуются новые нормализованные источники/иерархия/применимость и агрегаты партий подготовки. Это проектное решение архитектора, а не дата релиза; оно не возвращает a4 на схему 3/4. Форматы AEAD/backup остаются 1, криптографические ключи/привязки не меняются. Developer-флаги — сессионные и не мигрируют как полномочия.

Минимальные новые сущности с реальными FK и версионированными immutable body:

| Сущность | Связи и ограничения |
|---|---|
| learning_source_versions | student → users; source_kind/hash/revision; edition/ISBN/дата/происхождение; owner для ACL |
| learning_source_segments | FK source_version; range PDF и локальные printed labels/class/type; без полной книги |
| learning_source_matches | FK book/source_method versions; status/checker_version/evidence; UNIQUE(pair,revision) |
| learning_outline_nodes | FK curriculum и parent node; kind/order/number/optional/source segment; UNIQUE(curriculum,parent,order); leaf mapping к существующим topics |
| learning_skill_provenance | FK skill и source/match revision; origin methodical/ai/manual/legacy_unknown; старый текст навыка не меняется |
| learning_preparations / learning_preparation_batches | owner/curriculum/plan revision; задания по целям/резерву, child jobs/calls и budget; уникальная позиция партии/repair attempt |
| learning_job_events / learning_artifacts | FK job/preparation; append-only stage/attempt/correlation/time/status/code; нет секретов и разрешения целой книги |

Права узлов, совпадение curriculum у parent/leaf и отсутствие циклов проверять constraints/транзакционным валидатором; один UNIQUE с nullable parent недостаточен для уникальности корневых порядков, использовать отдельные индексы root/child. Новые коллекции и рубрики используют фактические topic IDs, а не текстовые номера. Добавить индексы owner/status, source_hash, curriculum/order и job/correlation. Очистка профиля/restore/Transfer охватывает новые таблицы.

### Порядок перехода

1. Остановить старый процесс, проверить installation/vault lock и версию исходного exe. Сохранить полную отдельную Portable-папку для возврата; до постоянного преобразования сделать проверенную зашифрованную копию контейнера. Неправильный пароль/неподдерживаемый формат ничего не меняют.
2. На копии/Staging выполнить 4→5 и маршрут 3→4→5 для 0.4.1; поддержанные более ранние схемы идут своим прежним маршрутом с единой итоговой публикацией. Snapshot/место/память и новая схема проверяются до atomic replace.
3. Старые IDs/роли/связи/обёртки/recovery/PERS/согласия и все learning_* / records сохраняются. Исторические program/task/payload/answers/observations/reviews/confirmations/success/work/originals/daily/calls не переоцениваются.
4. Старые темы представить плоскими legacy-узлами со старым position; hierarchy/ISBN/совместимость неизвестны до отдельного импорта. Не выдумывать главы, не делить § на несколько оценённых листьев. Новое дерево публикуется отдельной revision с предлагаемым сопоставлением.
5. Старый УМК/источник не удаляется. Отрицательная применимость к новому изданию — отдельный факт, который ограничивает новые навыки, а не переписывает старый план/рубрику.
6. Старые job stale остаются stale с исходным code/time. Можно показать derived explanation версии нового classifier. Не дописывать неизвестные payload/этапы. Running после прерванного обновления не запускать заново скрыто: показать interrupted и явное действие.
7. Прежние данные не получают новые запреты на уже начатые попытки. Для новых действий применить согласованную policy Q10/Q11: изучение/ДЗ доступны по будущим темам, точечный тест требует открытия либо родительского подтверждения прохождения, optional не блокируют следующую основную. Не выдавать подтверждений/проходов/успехов по позиции или обходу optional. Developer/trace выключены; старое согласие текста/фото сохраняет прежний scope.
8. Все новые таблицы и marker схемы 5 публикуются атомарно. Ошибка восстанавливает RAM/envelope или закрывает базу без дальнейшей записи; повтор не дублирует источники/узлы/партии. Проверить reopen, все доступы, новую запись, backup/restore и Transfer в пустое назначение.
9. Полные PDF из Downloads не переносятся в vault. Аналитические fixtures не становятся фактическим источником новой установки. Сравнить historical rows/ID/FK и хеши расшифрованных originals до/после; ciphertext после нового шифрования не обязан совпадать.
10. Возврат — старый exe с полной отдельной старой папкой, без downgrade/слияния новых записей. Экспорт trace не является учебным backup. Остаточные trace/import временные файлы от чужого vault не открываются после restore.
