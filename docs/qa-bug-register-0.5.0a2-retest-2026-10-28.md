### QA-050-04 — потеря runtime после отказа записи автопаузы

**Основание:** TIME-050-03/04 из [постановки исправлений](qa-remediation-requirements-0.5.0a1-2026-10-28.md): взаимное исключение работ, атомарная согласованность статуса, указателя и счётчиков. Это другое условие по сравнению с исправленным finish исторической A: сбой возникает в `Learning.tick()` при автоматической остановке.

**Предусловия:** тестовая семья; утверждённые программа/подборка; активная новая диагностика; свободный дневной лимит. Для воспроизводимости используется управляемый монотонный clock и временная подмена `store.save` на `OSError`. Рабочий диск специально не заполняется.

**Точные шаги для программиста:**

1. На синтетической семье начать новую попытку 8+2 и сохранить её ID.
2. Продвинуть тестовые монотонные часы на 181 секунду без учебных действий, достигнув idle-порога 180 секунд.
3. На время одного вызова `app.tick()` заставить `store.save()` выбросить `OSError`, то есть отказать checkpoint, которым оформляется автопауза. Перехватить ожидаемое исключение.
4. Убрать подмену записи; прочитать сохранённый статус попытки и `app.assessment_active`.
5. Вызвать обычный `app.tick()` ещё раз; проверить статус попытки, её `body.seconds` и дневной расход.

**Ожидается:** после отказа статус в БД и runtime остаются согласованными с предыдущим состоянием. Следующий успешный tick обрабатывает ту же попытку, начисляет допустимые 180 секунд и приостанавливает её. Допустимо другое явно спроектированное безопасное восстановление, но нельзя молча оставить сохранённую активную попытку без учёта.

**Фактически:** после исключения БД откатилась к `status='active'`, но `assessment_active=None`. После следующего успешного вызова статус всё ещё active, время попытки и дневной расход равны 0. Автопауза и начисление не повторяются. Ответы в этом тесте не удалялись; потеря истории ответов не заявляется.

**Причина по коду:** [learning.py](../tutor_ai/learning.py), `Learning.tick()`, строка с `self.s.assessment_active = None` внутри транзакции перед сохранением. При отказе `store.save()` SQL откатывается, runtime-указатель не восстанавливается. Следующий [Service.tick()](../tutor_ai/service.py) выбирает новый обработчик по этому указателю и уже не вызывает `learning_engine.tick()`.

**Автоматическое воспроизведение:** [test_additional.py](evidence/qa-retest-050a2-2026-10-28/test_additional.py), `test_failed_idle_checkpoint_keeps_attempt_runtime_consistent`. [Лог](evidence/qa-retest-050a2-2026-10-28/additional.log) фиксирует:

```json
{"after_failure_status":"active","runtime_still_points_to_attempt":false,"after_retry_status":"active","after_retry_seconds":0,"daily_seconds":0}
```

**Рекомендация:** публиковать runtime-переход после успешного checkpoint либо восстанавливать полный runtime при исключении. Проверить обе причины автопаузы: idle и окончание grace. Не восстанавливать неизвестное старое время по настенным часам.

**Критерии перепроверки:** отказ на автопаузе и последующее восстановление записи; отказ обычного tick; дневной предел/grace; повтор без двойного начисления; запрет параллельной работы; безопасный перезапуск; исходное воспроизведение QA-050-01. fault-проверку готового exe выполнять только на отдельной копии данных. До отдельного такого испытания не считать бинарную аварийную матрицу подтверждённой.

### QA-050-05 — режим «Подсказка» теряется при заполненном уточнении

**Основание:** [описание реализованного учебного процесса](implementation-0.5.0a1.md) и [руководство](user-guide-0.5.0a1.md) разделяют «Проверить полное решение», «Дать подсказку» и «Продолжить диалог». Режим хранится в новых метаданных a2, но должен также определять отправляемое модели задание.

**Предусловия:** ученик, разрешённое подключение ИИ. Для сравнения нужны три отдельные работы одного предмета с одинаковым решением, одинаковой revision и пустой предысторией диалога. Это исключает влияние старых реплик на сравнение.

**Воспроизведение через интерфейс:**

1. Создать работу по алгебре, сохранить и подтвердить решение:

   ```text
   3x+5=20
   3x=15
   x=5
   ```

2. Выбрать «Проверить полное решение», в «Уточнение» ввести `Поясни второй шаг`, отправить и дождаться результата. Завершить/приостановить возникшее занятие перед следующей работой.
3. Создать вторую новую работу с тем же решением; выбрать «Дать подсказку» и ввести такое же уточнение. Отправить и дождаться результата; приостановить занятие.
4. В третьей новой работе повторить с «Продолжить диалог» и тем же уточнением.
5. Сравнить «Фактически переданный учебный контекст» первых вызовов этих работ. Проверка не зависит от случайного качества ответа модели.

**Ожидается:** во втором запросе модель получает явное намерение hint и инструкцию дать подсказку. Текст уточнения дополняет режим, а не заменяет его. check/hint/follow_up различимы в переданном задании; это различие не остаётся только в локальном журнале.

**Фактически на исходниках и exe:** все три массива `messages` идентичны. В них есть общий system-текст, JSON с subject/solution/work_revision и пользовательское `Поясни второй шаг`. Выбранное значение intent отсутствует. Локальные `body.intent` при этом правильно различаются: check, hint, follow_up. Слова `intent=hint` в общем system-промпте одинаковы для всех запросов и не сообщают текущий выбор. Нельзя утверждать, что любая живая модель обязательно выдаст полный ответ; подтверждён именно дефект передачи режима.

**Причина:** [dialogue.py](../tutor_ai/dialogue.py), `work_messages()`: `current = follow_up.strip() if follow_up else INTENTS[intent]`. Непустое уточнение заменяет инструкцию выбранного режима. В базовом JSON subject/solution/revision поле intent также отсутствует. `Learning.work_check()` передаёт провайдеру полученный список сообщений; возвращённые metadata сами по себе в модель не отправляются.

**Доказательства:** второй тест в [test_additional.py](evidence/qa-retest-050a2-2026-10-28/test_additional.py); [фактические payload готового exe](evidence/qa-retest-050a2-2026-10-28/compiled-intent-result.json). На exe `check_equals_hint=true` и `hint_equals_follow_up=true`, при корректных локальных metadata.

**Рекомендация:** всегда включать текущее намерение в передаваемый контекст и добавлять уточнение отдельной репликой/полем. Сохранять intent у исторических реплик, не переписывая старые фактически отправленные запросы.

**Критерии перепроверки:** три режима с пустым и непустым уточнением; смена режима внутри одной работы; 2–4 пары реплик; старые версии и журнал a1; лимит 30 000 символов. Сравнивать реальные payload, а качество педагогического ответа проверять отдельным корпусом на живой модели.

## Как запустить независимые воспроизведения

Из корня проекта использовать настроенный `.venv/Scripts/python.exe`:

```powershell
.\.venv\Scripts\python.exe -X utf8 -m pytest docs/evidence/qa-retest-050a2-2026-10-28/test_additional.py -q -s --basetemp=build/qa-a2-repro-NEW
```

В текущем продукте ожидаются **два падения** утверждений правильного поведения. Для нового запуска выбрать новый суффикс `NEW`: pytest может очистить явно указанный basetemp. Не использовать путь рабочих данных.

Для QA-050-05 на exe: [драйвер](evidence/qa-retest-050a2-2026-10-28/run_compiled_intent.py) и [сценарий форм](evidence/qa-retest-050a2-2026-10-28/compiled_intent.js). Драйвер создаёт отдельную копию и loopback stub, платная модель не нужна. В данном окружении GUI запускался через терминал IDE. `passed=true` этого воспроизводящего сценария означает завершение измерения; поля равенства payload, равные true, подтверждают дефект, а не успешную приёмку продукта.

Обновление 0.4.1/0.5.0a1 и явная исправленная копия прошли отдельные проверки. Они не устраняют QA-050-04/05 и не являются основанием закрыть новые записи без исправлений.
