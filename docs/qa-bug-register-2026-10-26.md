## QA-001. Раскрытие отчёта после восстановления копии

**Требования:** ACL/Q-01, UX03-04.5, MIG03-06; U03-09/U03-24. Это дефект клиентского состояния: серверные ACL в воспроизведённом сценарии сработали.

**Предусловия:** в одной изолированной установке созданы родитель A, несвязанный родитель B и ребёнок C, связанный только с A. Сохранён backup с этими профилями. После backup ребёнок провёл занятие; A открыл его подробный отчёт.

**Шаги:**

1. Создать A, B и C; не связывать B с C.
2. Настроить тестовый провайдер и сохранить ручную копию с отдельным паролем.
3. Войти C, начать занятие «Линейные уравнения», сохранить и приостановить.
4. Войти A, открыть «Занятия и отчёты» и подробности этого занятия.
5. Открыть «Резервные копии» и восстановить копию из шага 2 с данными A.
6. На появившемся экране входа выбрать B и войти.
7. Перейти в «Занятия и отчёты».

**Ожидание:** нет детей и учебных данных C; восстановление и смена пользователя полностью очищают прежние персональные данные UI.

**Факт:** список детей B пуст; счётчик показывает 0 занятий, но ниже отображается прежний отчёт C с темой, снимком программы и текстом диалога. Отчёт отсутствует в восстановленной копии, но остаётся в памяти UI. Воспроизведено повторными изолированными GUI-прогонами.

**Доказательства:** [снимок экрана](evidence/qa-review-2026-10-26/screenshots/QA-001-cached-report-after-restore.png), [результат GUI](evidence/qa-review-2026-10-26/gui-exploratory-result.json), проверка `restore_clears_other_family_cached_report`: ожидалось false, получено true.

**Локализация:** `ui/app.js:298` очищает только lesson и drafts при restore; `refresh` на строках 33–43 не очищает report; `history` на строках 168–172 выводит state.report без проверки принадлежности актуальному ученику. Обработчик обычного logout очищает больше полей, но restore его не вызывает.

**Рекомендация программисту:** единая очистка персонального состояния после restore, выхода и смены учётки; проверка принадлежности report текущему snapshot перед выводом. Проверить также homework, profileEdit, результаты ИИ и провайдера, фильтры и сообщения. Не ограничиваться скрытием одного блока.

**Перепроверка:** повторить GUI-тест; дополнительно восстановить копию с другим составом детей, другим vault, исчезнувшим занятием; войти учеником/родителем без доступа. Ни текст, ни имя файла, ни результаты чужой работы не должны оставаться доступны.

## QA-002. Пустая служебная запись создаёт архив

**Требования:** UX03-04.1–04.2, U03-16. Пустая запись без учебного содержимого не должна создавать архив.

**Предусловия:** чистый синтетический ученик. Для проверки старых/служебных данных через fixture добавляется запись:

```json
{"id":"empty","subject":"math","topic":"unknown","created":"2020-01-01",
 "status":"complete","messages":[],"task":"","total":0}
```

**Шаги:**

1. Создать родителя и ребёнка на отдельной тестовой базе.
2. В транзакции записать приведённую запись типа session, владельцем назначить ребёнка.
3. Вызвать snapshot; проверить `students[0].archives.history`.
4. При просмотре UI открыть историю этого ученика.

**Ожидание:** `archives.history == {}`, математический архив в фильтре отсутствует.

**Факт:** возвращается `{"math_archive":"Математика — архив"}`. Одного status=complete достаточно независимо от отсутствия сообщений, задания и результатов.

**Доказательство:** [exploratory.log](evidence/qa-review-2026-10-26/exploratory.log), `test_empty_completed_session_does_not_create_archive`. Это проверка контракта на синтетической старой записи; возникновение такой записи через обычный текущий UI не утверждается.

**Локализация:** `aitutor/service.py:361–364`, условие `or s.get("status") == "complete"`.

**Рекомендация:** вычислять наличие учебных данных по содержимому, наблюдениям и результатам; один служебный статус не считать достаточным.

**Перепроверка:** пустые active/paused/complete; незавершённая запись с сообщением; завершённая с реальным результатом; другой ребёнок; разные периоды. Содержательные записи и статистика должны сохраниться.

## QA-003. Историческая физическая тема ошибочно считается математикой

**Требования:** UX03-04.1, UX03-04.4, MIG03-03–04, U03-19. Сохранять исходную предметную принадлежность и не назначать неизвестную тему наугад.

**Предусловия:** синтетическое историческое наблюдение с явным subject=physics и темой, отсутствующей в нынешнем стартовом каталоге:

```json
{"topic":"old-physics","subject":"physics","attempts_count":2,
 "correct_count":1,"mastery_score":50,"confidence":0.5}
```

**Шаги:**

1. Создать изолированную семью.
2. Записать наблюдение типа knowledge владельцу-ученику.
3. Вызвать snapshot и открыть карту знаний.

**Ожидание:** наблюдение остаётся физическим; неизвестное название темы не создаёт математический архив. Если предмет действительно архивный, использовать его исходную принадлежность.

**Факт:** snapshot заменяет subject на math_archive и добавляет «Математика — архив». Наблюдение выпадает из физического фильтра и появляется в математическом. Исходная запись в хранилище не переписывается; ошибка возникает при представлении.

**Доказательство:** [exploratory.log](evidence/qa-review-2026-10-26/exploratory.log), `test_retired_physics_topic_not_reclassified_as_math`.

**Граница:** fixture моделирует историческую/исключённую из каталога тему. Текущий встроенный банк такую тему сам не создаёт. Наличие подобных записей в реальной пользовательской базе не проверялось.

**Локализация:** `aitutor/service.py:346–348`: любой неизвестной теме назначается math_archive без учёта существующего subject.

**Рекомендация:** сохранить явно заданный корректный предмет; соответствие текущему каталогу применять при наличии обоснованного отображения. Для старых записей без предмета использовать явно документированное правило миграции.

**Перепроверка:** известные математические темы, неизвестная старая математика, неизвестная физика и другой архивный предмет; отсутствие дублей и переписывания исходного наблюдения.

## QA-004. Сохранение оформления не имеет явного результата

**Требование:** UX03-01.8: «Сохранение имеет явный результат».

**Шаги:**

1. Войти пользователем, открыть «Настройки».
2. Выбрать другой дизайн или цветовую тему.
3. Нажать «Сохранить».
4. Дождаться завершения операции.

**Ожидание:** доступное подтверждение успешного сохранения, отличающее его от предпросмотра.

**Факт:** настройки сохраняются и экран перерисовывается, но уведомления, статуса или иного явного подтверждения нет. Предпросмотр уже показывал выбранный дизайн до нажатия кнопки.

**Доказательство:** [GUI-результат](evidence/qa-review-2026-10-26/gui-exploratory-result.json), `theme_save_explicit_success`: ожидалось true, получено false. Фактическое сохранение и сохранность черновика отдельными проверками подтверждены.

**Локализация:** `ui/app.js:292`, обработчик theme выполняет RPC и refresh без статуса успешного результата.

**Рекомендация:** после успешной записи выводить «Оформление сохранено» в доступной области статуса; при ошибке записи показывать ошибку, позволяя повторить сохранение.

**Перепроверка:** оба дизайна и все три цветовых режима; успешная запись, ошибка диска, повторное сохранение, уход без сохранения. Сообщение об успехе появляется только после успешной записи.
