| Поле | Содержание |
|---|---|

Предусловия: отдельная синтетическая семья, ученик связан с родителем, разрешённое ИИ-подключение, свободный дневной лимит, подтверждённая работа по алгебре `3x+5=20; 3x=15; x=5`. Провайдер успешно отвечает до следующего запроса. Ошибок записи, лимита длины и реального исчерпания времени в исходном сценарии нет.

**Service-сценарий:** work_check/follow_up при монотонном clock=100, затем 160 и 220 успешно приняты, но last_action остаётся 100. При 281 четвёртый запрос вызывает tick и получает time_limit; занятие paused, учтено 180 секунд. Между последними действиями — лишь 61 секунда.

**Exe-сценарий:** отправить в одной работе три уточнения с ожиданием успеха и интервалами примерно 60/60 с; через 70 с после третьего проверить связанное занятие/дневной расход. По QA успехи получены примерно на 0,375 / 60,515 / 121,083 с; на 191,257 с занятие paused, seconds=180, хотя с последнего успеха прошло 70,174 с. Это подтверждение ложного idle, а не измерение SLA интерфейса. Периодический tick объясняет различие проявлений UI и нативного теста.

**Локализация:** `Learning.work_check()` устанавливает `last_tick = last_action = clock()` только при создании связанного занятия. Следующие вызовы выполняют `self.s.tick()`, не обновляя last_action. `Service.tick()` штатно применяет порог 180 секунд к устаревшей отметке. Нельзя исправлять это увеличением/отключением idle-порога или обновлением last_action на каждом фоновом tick.

## 3. Правило принятия учебного действия

Для этого пути необходимо явно отделить три события:

1. **Новый допустимый запрос ученика принят к выполнению.** Пройдены владелец/права, актуальная подтверждённая revision решения, intent, размер полного контекста, согласия, состояние соответствующего занятия, лимиты и идемпотентность. Успешная фиксация новой операции/задачи — граница обновления активности.
2. **Провайдер отвечает или фоновая задача публикует результат.** Это завершение обработки уже принятого действия, не новое действие ученика; оно не продлевает idle само по себе.
3. **Команда отклонена либо повторяет прежнюю operation_id.** Это не новая активность, даже если UI повторно показал старый успешный результат.

Перед принятием обработать накопленное время по прежней last_action и проверить, не наступили ли уже настоящий idle/grace. Новый запрос не должен задним числом отменять реально наступившую паузу. После успешного принятия обновить last_action только текущего связанного занятия, не обнуляя его накопленные seconds/daily и не теряя интервал от last_tick.

Если принятая и сохранённая задача затем получила ошибку/отмену провайдера, это не отменяет факт предыдущего допустимого действия. Но ошибка/ответ/автоматический повтор сети не дают дополнительной активности. Если новая операция не была принята/сохранена, обновления last_action нет. Это конкретизация существующего правила допустимого действия, а не новый способ считать ожидание сети учебной активностью.

## 4. Требования к исправлению

| ID | Требование | Критерий приёмки |
|---|---|---|
| ACT-050-01 | Обновлять активность каждого нового принятого запроса ДЗ | Повторные check, hint и follow_up обновляют last_action при успешном принятии операции, а не только при создании занятия. При интервалах меньше 180 с и свободном лимите занятие не получает ложный idle |
| ACT-050-02 | Сохранять одно корректно связанное занятие | Последовательные допустимые запросы одной работы обслуживают её текущее active-занятие; нет скрытого создания нового из-за устаревшей last_action. Проверять work/student/session, не менять активность другой работы, исторической попытки или чужого профиля |
| ACT-050-03 | Начислять время до обновления activity без потерь/дублей | Обычный checkpoint начисляет допустимый интервал от последнего успешного last_tick. Обновление last_action не сбрасывает last_tick так, чтобы этот интервал исчез. Прирост времени занятия и daily согласован; метки монотонны, часы ОС не используются для восстановления активности |
| ACT-050-04 | Сохранить настоящий idle на границе 180 с | Через 179 с после последнего принятого действия при свободном лимите — active; на 180/181 с — штатная пауза, начисление не более допустимого окна. После реального idle требуется действующее явное продолжение/новый разрешённый сценарий; нельзя продлевать старое окно задним числом |
| ACT-050-05 | Не обходить дневной предел и grace регулярным диалогом | Последовательные уточнения обновляют idle, но не обнуляют daily и не продлевают limit+900 с. При исчерпании применяются прежние ограничения. Нельзя оживить истёкшее занятие очередным check/hint/follow_up |
| ACT-050-06 | Не продлевать время фоновыми и историческими операциями | Tick, snapshot/overview, polling задач, просмотр меню/истории, чтение ответа, завершение другой попытки, загрузка старого журнала и автоматический сетевой повтор не обновляют last_action. Успех старого асинхронного ответа после ухода ученика не маскирует бездействие |
| ACT-050-07 | Сохранить идемпотентность и отказ до приёма | Повтор operation_id не считается новым действием, не начисляет повторно время/сообщения/usage. Чужой work, stale revision, неподтверждённое решение, неверный intent, превышение контекста и отсутствие согласия не обновляют last_action. Конфликт содержимого той же операции не создаёт новый запрос |
| ACT-050-08 | Обеспечить атомарность при записи/публикации | Отказ фиксации новой операции не оставляет runtime с новой активностью без сохранённого принятия. Если штатный checkpoint успел успешно сохранить время до отказа запуска задачи, его last_tick/seconds не откатываются к несовместимому состоянию и не начисляются второй раз. Отказ checkpoint сохраняет согласованное состояние и безопасный повтор, не возвращает QA-050-04 |
| ACT-050-09 | Различать принятие и исход фоновой задачи | После сохранённого принятия не откатывать последнюю активность только из-за последующего network/timeout/cancelled/stale_result. Завершение задачи не обновляет её повторно; журнал сохраняет принятый запрос и реальный статус. После logout/restore старый результат не меняет активность нового контекста |
| ACT-050-10 | Сохранить корректную границу при долгом ожидании | Если после единственного принятого запроса новых действий нет 180 с, ожидание провайдера/polling не удерживает занятие бесконечно активным. Сохранить результат/статус задачи и правила его применения, не создавать новую активность из времени ответа |

Реализационный способ — общая операция принятия/фиксации активности или существующий корректный механизм Service — выбирает разработчик. Перенос присваивания last_action перед всеми проверками, обновление на каждую перерисовку либо безусловный rollback всех часов при любом исключении требованиям не соответствуют.

| Короткие запросы вплоть до limit/grace | Idle не ложный, но предел расхода не обходится, время не обнуляется |
| Та же operation_id спустя время / другой fingerprint | Не новая активность; возвращён прежний результат либо конфликт, без дубликатов |
| Отказ валидации/прав/согласия/контекста/revision | Нет обновления активности/сетевого запроса. Текст/черновик и прежняя история сохранены |

| Принятая задача → ошибка/отмена/поздний результат | Одно обновление на приёме, нет обновления на завершении; результат/ошибка в журнале, old-context/stale не изменяют новую работу |
| Настоящий idle до нового запроса / долгая сеть без действий | Просроченное состояние не скрывается; применён прежний порядок продолжения, окно ожидания не продлевается автоматически |
| Перезапуск, restore, смена ученика и работы | Время закрытого приложения не начисляется, требуется явное продолжение; чужие журналы/таймеры не затронуты |

Повторить на новом Portable exe исходный сценарий с реальным clock: успешные уточнения примерно через 60/60 с, затем наблюдение через 70 с; одно active-занятие, расход продолжает учитываться. Проверять секунды/нативный snapshot и журнал, а не округлённые минуты. Отдельно дождаться настоящего idle после последнего запроса и подтвердить паузу. Не заменять реальное ожидание только искусственными часами или только UI-надписью.

Сценарий exe имеет `passed=true` при завершении измерения; функциональный критерий — `active_dialogue_preserved=true` при соблюдении предусловий и согласованные счётчики. Прежний результат false остаётся историческим доказательством, не переписывается. Анализ не требует живых платных моделей: тестовый провайдер достаточен для доказательства таймера.
