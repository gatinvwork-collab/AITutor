# Реестр дефектов Tutor-AI 0.5.0a1

Дата проверки: 28.10.2026. Основание: [README](../README.md), [статус реализации](implementation-0.5.0a1.md), [руководство](user-guide-0.5.0a1.md). Полный ход проверки и границы покрытия: [протокол QA](qa-report-0.5.0a1-2026-10-28.md).

Объект: текущие исходники и `dist/Tutor-AI-0.5.0a1.exe`; SHA256 exe `dd818a749ebb4964728432f073e309f8c90c49f96bd5b7017f52b1332eb36ebf`. Все три дефекта воспроизведены на этом exe. Рабочие данные пользователей не использовались. Код приложения не исправлялся.

Приоритеты: P1 — высокий, нарушение учёта времени/контроля работы; P2 — средний, неверный пользовательский контекст с возможностью обхода вручную. Все записи имеют статус **Открыт, подтверждён**.

| ID | Приоритет | Дефект | Доказательство |
|---|---|---|---|
| QA-050-01 | P1 | Завершение приостановленной попытки A выключает таймер активной B | Исходники: 30 секунд не начислены; exe: за 6,5 секунд активное время B не изменилось |
| QA-050-02 | P2 | Следующее уточнение ДЗ не получает предыдущий вопрос ученика | В фактическом втором запросе нет первого уточнения, хотя в локальном журнале оно сохранено |

## QA-050-01 — операция с исторической диагностикой отключает активную

**Область:** новые диагностики схемы 4, учёт времени, взаимное исключение занятий. Это отдельный дефект нового обработчика; успешная регрессия исторических операций старых занятий QA-005/006 его не закрывает.

**Предусловия:** тестовая семья; подключение ИИ; опубликованная программа хотя бы с одной темой и отдельно утверждённая подборка, достаточная для двух попыток 8+2. Синтетический банк в приложенном автотесте создаётся подменённым провайдером, без платных запросов. В производственном интерфейсе можно использовать уже утверждённую подборку.

**Воспроизведение через UI:**

1. Войти учеником, открыть «Учебный процесс», загрузить программы и работы.
2. Начать точечную диагностику A. Ответить на все восемь обязательных вопросов, два сложных ответить или явно пропустить.
3. Нажать «Сохранить и приостановить» для A, оставив её незавершённой.
4. Начать диагностику B по той же утверждённой подборке.
5. В карточке приостановленной A нажать «Завершить попытку».
6. Оставить B активной минимум на один период фонового учёта, затем проверить её активное время и дневной расход. Для точного результата использовать API/приложенный тест: интерфейс округляет минуты.

**Ожидается:** команда применяется к A. B продолжает учитываться; её таймер, дневной расход и ограничения продолжают работать. Допустимо явно запрещать завершение A во время B, если это будет согласованным поведением.

**Фактически:** A завершается, B остаётся `status='active'` в БД, но `Service.assessment_active` становится `None`. Независимый тест на исходниках: после продвижения монотонных часов на 30 секунд у B `seconds=0`. На exe до/после ожидания 6,5 секунды одинаковое значение `0.02067880000686273`. Потери ответов в этом сценарии не зафиксировано; нарушен учёт активной работы. Возможность обхода иных ограничений следует проверить при исправлении, она отдельно не заявляется как измеренный результат.

**Локализация:** [learning.py](../tutor_ai/learning.py), `change_status()`: внутри `save()` поле `assessment_active` безусловно обнуляется для любого завершения/паузы, независимо от того, какая попытка активна. `Service.tick()` выбирает обработчик по этому полю. Аналогично сбрасываются общие отметки времени.

**Рекомендация программисту:** менять указатель и временные отметки только при переходе соответствующей активной попытки; проверять согласованность указателя с сохранённой активной попыткой. Сохранить атомарность при отказе checkpoint.

**Повторная приёмка:** A paused → B active → finish A; B должна продолжить начисление времени без двойного учёта. Проверить отказ записи, дневной предел, idle, завершение без B, повтор operation ID, перезапуск и запрет параллельных занятий.

## QA-050-02 — потеря предыдущего уточнения в коротком диалоге ДЗ

**Область:** «Продолжить диалог», A14, фактический контекст модели. [Постановка §2.6](learning-feedback-developer-specification-2026-10-28.md) требует продолжения одного контекста; объявленное ограничение длинного диалога не объясняет потерю уже второго короткого сообщения.

**Предусловия:** ученик, работа с подтверждённым текстом и разрешённым ИИ-подключением. В тесте использовано решение `3x+5=20`, `3x=15`, `x=5`.

**Воспроизведение:**

1. В работе выбрать действие «Продолжить диалог».
2. Ввести `QA_CONTEXT: объясни вычитание пяти`, отправить, дождаться завершения задачи и обновить состояние.
3. В той же работе отправить второе уточнение: `Поясни мой предыдущий вопрос подробнее`.
4. В журнале работы раскрыть «Фактически переданный учебный контекст» для второго запроса. Для проверки переноса контекста не требуется субъективно оценивать ответ модели.

**Ожидается:** второй запрос содержит предыдущую пару вопрос–ответ или эквивалентное явное сохранение смысла первого уточнения, с корректными ролями сообщений.

**Фактически:** отправляются system, исходное решение user, предыдущий ответ assistant, только текущее уточнение user. Первое уточнение `QA_CONTEXT` отсутствует. Оно остаётся в записи первого вызова локального журнала, то есть данные на диске не утрачены, но модель не получает вопрос, на который ранее ответила. Воспроизведено и на исходниках, и через формы готового exe.

**Локализация:** [learning.py](../tutor_ai/learning.py), `work_check()`: цикл `for call in prior[-4:]` добавляет только `call['response']`, не соответствующие пользовательские реплики. Ограничение 30 000 символов в тесте не достигнуто.

**Рекомендация:** собирать контекст из реальных упорядоченных реплик user/assistant, сохраняя ссылку на версию работы; при ограничении длины сокращать целые пары или явно сообщать о недостатке контекста. Не дублировать вложенные снимки предыдущих запросов.

**Повторная приёмка:** 2–4 коротких уточнения; check → follow_up и hint → follow_up; после изменения версии решения; после перезапуска; ошибка/отмена предыдущего вызова; превышение лимита. Локальная полная история сохраняется, секреты в контекст не попадают.

## QA-050-03 — переход из предмета создаёт ДЗ по другому предмету

**Область:** существующая кнопка каталога «Проверить ДЗ по этому предмету», интеграция с новой формой. [Руководство §«Домашние задания»](user-guide.md) прямо описывает предварительный выбор предмета этой кнопкой.

**Предусловия:** ученик; новый вход, предмет в новом учебном процессе ещё не менялся. ИИ для этого сценария не требуется. При наличии ранее выбранного предмета вместо алгебры может сохраниться другой старый выбор.

**Воспроизведение:**

1. Открыть «Предметы», выбрать «Информатика».
2. Нажать «Проверить ДЗ по этому предмету».
3. При первом открытии нажать «Загрузить программы и работы».
4. Посмотреть поле «Предмет» и подпись кнопки создания работы.
5. Нажать «Создать работу…»; проверить предмет созданной записи.

**Ожидается:** информатика выбрана и передана в создаваемую работу. При переходе из физики/геометрии аналогично сохраняется исходный предмет.

**Фактически на exe:** `requested='informatics'`, `selected='algebra'`, `created='algebra'`. Выбор виден в форме, поэтому пользователь может исправить его вручную, однако обещание кнопки нарушено и возможна незаметная проверка в неверном контексте.

**Локализация:** [app.js](../ui/app.js), обработчик `subject-homework` записывает `state.hwSubject`; [learning.js](../ui/learning.js), `learningPage()` использует `state.learnSubject` либо первый предмет. `homeworkPage()` уже возвращает новый `learningPage()`. Обработчики диагностики рядом используют новый `learnSubject`.

**Рекомендация:** передавать выбранный предмет новому экрану единым способом и согласовать состояние формы с создаваемой работой. Сохранить уже существующие работы с прежними предметами.

**Повторная приёмка:** переход из каждого из четырёх предметов, до и после загрузки данных; затем изменить выбор в учебном процессе и снова перейти из другого предмета; повторить после logout/login. Проверить фактический subject новой работы, доступность Python только для информатики и отсутствие переименования старых работ.

## Замечание к тестовой инфраструктуре T-050-01

`gui_smoke` и `gui_import_032` обращаются к старым элементам формы ДЗ, недоступным на новом маршруте; `gui_transfer_040` жёстко ожидает `0.4.0`. Они завершаются с ошибкой в текущей версии. Это требует обновления регрессионных сценариев, но само по себе не подтверждает три дополнительных дефекта приложения. Исходные сценарии оставлены без изменений; для нового UI выполнены отдельные [12 проверок ДЗ](evidence/qa-independent-050-2026-10-28/gui-current-homework-result.json), а перенос повторён с единственным изменением ожидаемой версии — [9 проверок](evidence/qa-independent-050-2026-10-28/gui-transfer-current-result.json). Переход из предмета проверен отдельно и оформлен QA-050-03.
